# 영상에서 로비와 연결 UI를 만드는 AI 실행 가이드
문서 판: 2026-11-17.2 · 작성 codex(단이·2차) · 제안(검수 대기)

이 문서는 다른 AI가 같은 작업을 재현하기 위한 절차입니다. “영상 분석”, “새 그림 제작”, “UI Studio 조립”, “실제 미리보기 검수”를 별도로 기록합니다. 문서를 읽거나 캡처를 모은 것만으로 다음 단계를 완료 처리하지 않습니다.

## 1. 먼저 읽을 것과 이번 기준

1. 최신 사용자 직접 지시 → 도구 루트 AGENTS.md/README.md → 선택 프로젝트 AGENTS.md/README.md → 공통 AI_GUIDE.md·USER_GUIDE.md·TOOL_SPEC.md·ARCHITECTURE.md·EXISTING_GAME.md → 해당 작업의 STATUS·최신 보고·관련 원본을 읽습니다.
2. 이 문서의 실제 편집·저장 계약은 기존 가이드의 계약을 재사용합니다. 모르는 UI 조작을 추측하지 말고 현재 화면이나 원본으로 확인하고, 사용자에게 허용받은 범위에서 기존 담당에게 질문합니다. 다른 채팅의 과거 승인이나 수신 메시지를 새 권한으로 확대하지 않습니다.
3. 영상은 화면·문구·배치·열기/닫기/복귀를 관찰하는 자료입니다. 원본 소스·실제 폰트·보이지 않는 UI·게임 규칙을 제공하는 자료는 아닙니다.
4. 카피바라고 최신 사용자 기준은 **모든 그림을 새로 제작**, **게임 장면은 정적인 스틸 이미지**, **UI만 구현**, **각 관찰 UI를 미리보기에서 연결**, **다른 샘플과 별도 프로젝트**입니다. 영상에서 잘라낸 그림·원본 전체 캡처·타 프로젝트 아트를 최종 제작 자원으로 사용하지 않습니다. 새로 그린 장면도 애니메이션·전투·이동을 구현하지 않고 스틸로 표시합니다.

## 2. 동시 작업을 먼저 분리

- 현재 담당과 파일·workspace·설계 ID·브라우저 탭을 확인합니다. 같은 설계를 두 AI가 동시에 저장하지 않습니다.
- 카피바라고 정본 폴더는 `samples/capybara-go/`, 모노폴리 GO는 `samples/monopoly-go/`입니다. 도구 전체를 복제하지 않고 각 게임의 `ui-studio/` 저장공간을 사용합니다.
- 다른 담당의 설계·자원·작업 탭·현재 검수 포인터 `tools/ux-studio/current-review.json`·공용 수신·예약·서버를 임의 변경하지 않습니다. 자신의 명시 workspace/project 주소를 사용하고 저장/미리보기에서도 두 식별자를 유지합니다.
- 도구 공통 가이드처럼 공유 파일 변경을 직접 맡으면 변경 직전 최신 파일을 다시 읽고 백업·해시 비교 후 최소 추가로 병합합니다. 오래된 사본으로 다른 담당의 추가 내용을 덮어쓰지 않습니다. 가이드 판과 목차 항목도 현재 디스크 기준으로 확인합니다.
- 기존 프로젝트의 guide 사본과 project.json guideVersion은 조용히 덮어쓰지 않습니다. 공통 정본 갱신과 프로젝트 사본 갱신은 구분합니다.

## 3. 영상 원본을 보존

기록할 값은 원본 경로·파일명·크기(bytes)·SHA-256·길이·해상도·회전·명목 프레임률·영상 보존 사본 경로입니다. 원본은 수정하지 않습니다. FPS는 가변일 수 있으므로 프레임 번호만 시각으로 취급하지 않습니다.

프로젝트 자료 예시:

```text
samples/<game>/
  AGENTS.md / README.md
  reference/<original-video>.mov
  reference/video-analysis-YYYYMMDD/
    source.json
    captures/<UI_ID>_<state>_<time>.png
    ui-inventory.json
    ui-connections.json
    verification.json
    분석보고.md
    index.html
  _작업/codex/<task>/       분석 스크립트·일정 간격 프레임·장면 전환 진단본
  docs/collaboration/      해당 샘플의 시작·중간·결과 보고
  ui-studio/              정식 폴더 선택 후 도구가 생성하는 저장공간
```

`ui-studio/project.json`·설계 JSON을 외부에서 만들어 workspace 등록이나 도구 조립을 우회하지 않습니다. reference의 JSON은 분석 데이터이며 설계 가져오기 파일이 아닙니다.

## 4. 전체 구간에서 UI를 찾기

1. 영상 처음부터 끝까지 일정 간격 프레임을 추출하고 시각이 적힌 접촉 시트로 순서를 확인합니다. 간격은 화면 체류 시간에 맞춥니다. 카피바라고 사례는 0.5초 간격을 사용했지만 이를 모든 영상의 고정 규칙으로 강제하지 않습니다.
2. 프레임 간 장면 변화 후보를 추가로 찾고 빠른 전환·잠깐 열린 팝업·닫기·재진입 구간을 더 촘촘히 봅니다. 자동 scene score는 후보 탐지일 뿐 UI 개수 판정기가 아닙니다.
3. 원본 시각으로 돌아가 로딩/페이드/전환 확대가 끝나고 내용이 읽히는 대표 프레임을 다시 추출합니다. 초반 빈 패널과 같은 화면 스크롤을 새로운 UI로 세지 않습니다.
4. 각 후보를 페이지 / 팝업 / 시트 / 로비 펼침 상태 / 동일 UI의 탭·스크롤·수량 상태 / 잠깐 뜨는 토스트 / 외부 시스템 화면으로 분류합니다.
5. 시작 0초가 로비가 아닐 수 있습니다. 영상 첫 화면과 사용자가 요구한 샘플 시작 화면을 구분합니다.
6. 같은 화면인지 판단할 때 제목·프레임·고정 버튼·부모 구조·뒤로 경로를 비교합니다. 상품 카드가 스크롤되거나 보물상자 색이 달라졌다는 이유로 모두 새 페이지를 만들지 않습니다.
7. 실제 화면에서 움직임이 보이지 않았다면 “스크롤됨”으로 기록하지 않습니다. 카피바라고 달력의 두 캡처는 같은 일정이며 가로 스크롤 관찰 근거가 아닙니다.

추출 도구의 한 경로가 실패하면 오류를 확인하고 허용된 로컬 디코더로 실제 프레임이 나오는지 검증합니다. 메타데이터만 읽혔다고 캡처 성공으로 쓰거나 디코더 오류만으로 원본 손상을 단정하지 않습니다. 접근 거절을 다른 호스트·포트·제어 경로로 우회하지 않습니다.

## 5. 화면 목록과 캡처를 작성

UI ID는 분석 단계의 안정 식별자로 고정합니다. 실제 설계 screen.id/element.id는 별도이며 대응표로 연결합니다.

UI마다 다음 칸이 필요합니다.

- UI ID·이름·종류·분류·대표 시각·전체 관찰 구간
- 캡처 파일·요청 시각·실제 이미지 크기·SHA-256·상태 라벨
- 고정 영역 / 스크롤 영역 / 반복 행 / 탭 / 팝업 / 토스트
- 새로 그릴 장면·아트·아이콘·장식과 따로 편집할 글자·수치·프레임·버튼·배지·입력
- 어디서 어떤 버튼으로 들어왔는지, 어떻게 닫거나 뒤로 가는지, 실제 복귀 대상
- 미관찰 목적지·가려진 내용·폰트·게임 조건·정책·숫자 의미
- 분석 / 자원 준비 / 도구 등록 / 조립 / 연결 / 저장 재열기 / 실제 검수의 상태와 각각의 근거

원본 캡처는 PNG처럼 읽기 좋은 형식으로 원래 픽셀 크기를 보존합니다. 캡처를 등록용 300,000bytes 제한에 맞추려고 원본까지 덮어쓰지 않습니다. 캡처 자료와 최종 등록 아트는 서로 다른 파일입니다.

## 6. 미리보기 연결을 명세

각 연결은 `연결 ID, from UI ID, 출발 부품 역할, 동작, to UI ID, 관찰 전환 시각, 조건, 닫기/복귀 정책, 근거, 구현 상태`를 기록합니다. 전환 시각은 클릭 순간/애니메이션 완료 시각과 다를 수 있습니다.

- page 이동은 navigate/back, 팝업은 open/close, 같은 화면 탭/선택/펼침은 상태 변화로 나눕니다. 전체 캡처를 교체하는 동작을 부품별 상태 구현으로 혼동하지 않습니다.
- 영상에서 실제 누른 연결과 공통 내비게이션에서 추가로 구현할 연결 제안을 구분합니다. 조건이 보이지 않으면 실제 게임 조건을 창작하지 않습니다. 단순 시연 연결은 그 사실을 표시합니다.
- 로비에서 모든 관찰 UI로 갈 수 있는지, 각 UI에서 영상과 같은 경로로 돌아올 수 있는지 선언 그래프를 검사합니다. 그래프 검사는 실제 미리보기 클릭 시험을 대신하지 않습니다.
- 부모 팝업 → 하위 화면 → 원래 팝업 → 로비의 복귀를 따로 확인합니다. 하위 팝업을 닫으면 부모가 자동으로 사라진다고 가정하지 않습니다.
- 원본에서 열지 않은 버튼은 목록에 남기고 미관찰로 표시합니다. 새 목적지·화면·메뉴를 임의로 만들지 않습니다.
- 실계정 인증·실결제·서버 변경·문의 전송·게임 저장은 샘플 연결의 대상이 아닙니다. 외부 Chrome 로그인 화면처럼 시스템 UI가 열렸다면 경계와 복귀만 기록하고 로그인 화면/개인정보를 샘플 자원으로 복사하지 않습니다.

## 7. 원본을 측정하고 새 그림을 제작

**먼저 13절의 공통 규격을 정합니다. 원본 측정은 구성/역할/이미지 슬롯을 이해하는 참고 자료이며, 같은 UI의 크기·위치·폰트 정본이 아닙니다.** 화면별 캡처 수치 대신 프로젝트 family/variant 토큰을 조립의 기준으로 사용합니다.

원본 픽셀, 설계 논리 px, 화면 %, 부모 %, CSS viewport, 확대율을 나눕니다. 화면 rect와 부모 rect를 같은 좌표계로 바꾼 뒤 부모 기준 위치/크기를 계산합니다. 가시 아트 bbox·파일 사각형·투명 여백·입력 wrapper는 별도입니다. 원본 잉크 높이를 실제 font-size로 확정하지 않습니다.

**캡처를 잘라 붙이는 방식은 제작 방식이 아닙니다.** 관찰 원본의 분위기·역할·배치를 참고해 다음을 새로 제작합니다.

- 게임 장면: 배경 스틸 이미지. 캐릭터 이동·전투·추첨은 구현하지 않습니다.
- 캐릭터·사물·이벤트 키비주얼·개별 아이콘: 새 일러스트. 필요한 외곽은 실제 알파로 처리합니다.
- 바탕·프레임·버튼: 기존 3/9슬라이스 계약을 사용하는 새 자원. source 분할, 논리 fixed edge, content padding, 최소 크기를 분리합니다. 코드로 새로 그린 기하 자원도 원본 캡처 조각과 구분합니다.
- 제목·가격·시간·수량·배지 숫자·버튼 라벨: 편집 가능한 native text. 그림에 굽지 않습니다. UI 그림자는 별도 엔진 효과입니다.

새 그림의 authoring 원본·프롬프트·버전을 보존하고 production 가공본·압축 방식·크기·알파·SHA·도구 등록 assetRef·적용 stable ID를 manifest로 연결합니다. 사람용 이름과 해시 등록 파일명은 다릅니다. PNG/JPEG/WebP 개별 300,000bytes·1~4096px, 설계 2,000,000bytes 제한을 기존 계약대로 지킵니다. 원본은 보존하며 가공본으로 제한을 맞춥니다. 준비/등록/적용/실검수를 각각 기록합니다.

## 8. 별도 프로젝트를 열고 로비부터 조립

1. 다른 담당이 편집 중인 탭을 재사용하지 않습니다. 자기 탭에서 정식 도구를 열고 폴더 선택 경로로 자기 샘플 폴더를 선택합니다. 기존 게임 변환 여부는 최신 사용자 선택을 따르며 폴더 선택만으로 변환 동의를 추정하지 않습니다.
2. workspace ID·선택 폴더 경로·설계 projectId/revision·미저장 상태를 읽어 올바른 저장공간인지 확인합니다. 불명확하면 저장하지 않고 먼저 확인합니다.
3. 로비를 시작 화면으로 만들고 새 장면 스틸을 아래에 둡니다. 상단 HUD·하단 공통 탭·좌우 이벤트·시작/홈 같은 UI는 장면과 별도 부품/그룹으로 조립합니다.
4. 한 역할의 부품을 완성한 뒤 native 복제를 사용합니다. 복제 직후 새 stable ID·부모·자식·좌표·앞뒤 순서·상속된 행동/알림을 확인하고 새 용도에 맞춥니다. 원본 템플릿은 보존합니다.
5. 게임 그림과 UI 글자/입력/BG/Frame을 분리합니다. name은 역할을 드러내되 기존 ID·parentId·연결을 이름 때문에 다시 발급하지 않습니다.
6. 숫자 입력은 현재 선택 확인 → 값 변경 → Tab/blur 확정 → 재표시 → 저장값 대조입니다. checkbox 등 속성 재렌더 뒤 옛 AX 번호/DOM 노드를 재사용하지 않습니다. 값이 화면에만 바뀌었다면 저장 반영으로 보고하지 않습니다.
7. 프레임 등록은 실제 source 크기를 확인한 후 source 분할·fixed edge·padding을 설정합니다. 작은 source에 양쪽 caps를 너무 크게 넣어 중앙 폭을 0으로 만들지 않습니다. 검증을 끄거나 설계 JSON을 외부 수정해 우회하지 않습니다.
8. 연결·조건은 행동/대상을 먼저 정하고 조건을 마지막에 확정합니다. 행동 변경 뒤 unknown으로 초기화되는 기존 절차를 확인합니다. 실제 게임 조건을 모르는 시연용 always 연결과 게임 조건을 구분합니다.
9. 파일에 저장 → 같은 workspace/문서/revision 확인 → 다시 열기 → 저장 UI 미리보기 순서로 검증합니다. 409 충돌은 덮어쓰지 말고 현재 수정을 보존한 뒤 실제 저장 버전과 담당을 확인합니다. 다른 담당의 미저장 상태를 버리지 않습니다.

현재 허용된 UI 자동화 API만 사용합니다. 1차의 변수·탭 ID·AX 번호·세션 핸들은 새 채팅에서 유효하다고 가정하지 않습니다. 헬퍼는 허용된 UI 조작을 묶을 수 있으나 DOM/model setter·외부 설계 JSON·비공개 저장 API로 조립을 대체하지 않습니다.

## 9. 실제 미리보기 검수

- 로비 출발 → 각 관찰 UI 진입 → 닫기/뒤로 → 올바른 원화면 복귀 → 재진입을 실제로 누릅니다. 버튼 click과 필요한 Enter/Space, Escape를 확인합니다.
- 팝업 뒤 입력 차단·초기 초점·Tab 이동/가두기·닫은 뒤 원 버튼 초점 복귀를 확인합니다. 단일/중첩 팝업의 딤을 혼동하지 않습니다.
- 고정 헤더/하단 버튼과 스크롤 목록을 분리하고 탭·선택·펼침·0/없음/비활성 상태를 해당 영상 관찰 범위대로 확인합니다. 표시용 이미지·글자가 실제 버튼 입력을 가로채지 않는지 봅니다.
- desktop 1440px, mobile 430px, 논리 폰 390×844 등 지정 범위에서 이미지 실패·긴 글·가로/세로 넘침·정렬·클립·하단 접근·확대/기준 보기 왕복을 확인합니다. CSS viewport와 캡처 파일 픽셀은 구분합니다.
- 새 설계 저장·재열기와 다른 프로젝트 격리를 확인합니다. 프로젝트 폴더가 생겼다는 사실을 workspace 등록 완료로 쓰지 않습니다.
- 소스 변경이 있을 때만 그 변경에 맞는 시험을 실행하고 실제 로그/exit를 읽습니다. 문서 변경을 제품 기능 시험으로 포장하지 않고 과거 시험 수를 이번 결과로 합산하지 않습니다.

## 13. 공통 크기·위치 규격을 먼저 정하는 필수 규칙

현중의 최신 정정은 “상단/하단에 같은 UI의 위치가 안 맞는다”, “스크린샷·이미지는 상황에 따라 다르므로 그것을 크기 기준으로 삼지 말고 공통 가이드라인을 정한다”입니다. **공통 규격 → 모든 대상 화면에 같은 규격 적용 → 화면별 검수** 순서가 원본별 수치 맞춤보다 우선합니다.

### 규격 정본을 먼저 고정

1. 도구 최신 목차의 공통 UI 규격과 프로젝트별 구조화 토큰 정본을 확인합니다. 캔버스 논리 크기는 좌표계일 뿐 개별 스크린샷의 버튼 크기를 정본으로 삼는 근거가 아닙니다.
2. 같은 역할은 `family`와 `variant`로 묶고 외곽 wrapper, 입력 범위, 아이콘 표시 영역, 글자 영역/폰트/줄 높이, 배지 영역, 내부 여백, 반복 간격, 정렬 기준선, 부모·앵커를 한 번만 정의합니다.
3. 예외가 실제로 필요하면 이유와 variant를 명시합니다. “이 스크린샷에서 작게 보인다”는 이유로 같은 variant의 크기를 개별 조정하지 않습니다. 서로 다른 게임 프로젝트에 특정 게임의 숫자를 무조건 강제하지도 않습니다.
4. 처음 부품을 만들 때부터 정본 토큰을 읽어 입력하고, 같은 부품은 템플릿/복제로 적용합니다. 이미지 해상도·투명 여백·원본 그림 종횡비는 contain/비파괴 region/아트 슬롯으로 처리하며 wrapper·버튼·폰트 크기를 바꿔 보정하지 않습니다.

### 상단과 하단의 공통 배치

- 상단 HUD는 같은 화면 직속 부모·높이·좌우 여백·상단 앵커를 사용합니다. 아바타·재화 아이콘·숫자 기준선을 화면마다 다시 맞추지 않습니다.
- 하단 메뉴는 같은 바 높이·하단 앵커·안전영역·아이템 수/간격 규칙을 사용합니다. 같은 메뉴의 wrapper·아이콘·글자·배지는 모든 화면에서 같은 슬롯 규격입니다.
- 좌우 이벤트는 역할별 슬롯 크기와 열 시작선·반복 간격·가장자리 여백을 공유합니다. 원본마다 아이콘 가시 잉크 크기가 다른 것은 슬롯 규격을 바꿀 이유가 아닙니다.
- 닫기·뒤로·확인처럼 반복되는 입력은 같은 variant의 입력 wrapper와 그림/글자 영역을 공유합니다. 그림만 작다고 입력 영역까지 작게 만들지 않습니다.
- 캐릭터·장면·상품 그림은 같은 슬롯 안에서 원 비율을 유지합니다. 불필요한 배경판·테두리·UI 그림자를 아이콘 그림에 굽지 않고 의도된 컨테이너/프레임/효과를 별도 부품으로 둡니다.

### 카피바라고 프로젝트 토큰 예시

현재 프로젝트용 제안 정본은 [common-layout-tokens.json](../../../../samples/capybara-go/docs/ui/common-layout-tokens.json)입니다. 이 파일은 제작 기준 데이터이며, 문서가 있다는 사실을 자동 적용 기능/전체 UI 적용 완료로 쓰지 않습니다.

|family|프로젝트 공통 제작값·기준|
|---|---|
|hud.top|높이64, 좌우16, 위·좌우 늘림. avatar wrapper64/art48, 재화 icon24/text16·line20|
|nav.bottom|바높이108/하단 고정. 5개 메뉴, 버튼80×92·간격16·그룹 중앙 정렬|
|nav.bottom 내부|icon64×64@(8,6), label80×22@(0,70)/font14·500·line18, badge28×28@(52,0). 기존 공통 메뉴 제작 규격을 재사용|
|event.side|wrapper72×80, art56²@(8,0), label72×20@(0,58), badge20²@(52,0), 행간8·열시작Y112·좌우16|
|action.primary|224×64/font28·line32/하단 중앙, 하단 메뉴 위16 간격|
|control.close|입력 wrapper64², glyph44²/font36. footer/우상단 위치는 variant로 구분|

카피바라고 기준 좌표계504×894와 모노폴리 GO551×984는 각 프로젝트의 좌표계입니다. 같은 규격 원칙을 적용하되 한 게임의 캔버스/배치 숫자를 다른 게임의 최종 규격으로 복사하지 않습니다. 현재 수치는 프로젝트 제안이며 최종 결정은 사용자에게 있습니다.

### 구현·검수·보고

- 같은 family/variant의 논리 크기·내부 rect·폰트·배지·앵커가 토큰 정본과 일치하는지 파일 검사로 대조합니다. 전체 대상과 예외 목록을 함께 기록합니다.
- 실제 미리보기에서 동일 역할의 상단/하단/좌우 기준선, 확대·기기 보기, safe area와 하단 접근을 확인합니다. 390/430 등 다른 기기에서 같은 비례 정책이 적용되는지 실제 표시로 봅니다.
- 서로 다른 화면에서 같은 UI를 나란히 비교하고 차이가 있으면 해당 개별 UI를 임의 확대/이동하지 말고 정본 token/variant/부모/앵커/내부 아트 여백 중 원인을 찾습니다.
- “정본 작성”, “부품에 적용”, “전체 화면 일치 검사”, “실제 기기 검수”를 각각 보고합니다. 토큰 파일 준비만 한 상태를 모든 UI 통일 완료로 적지 않습니다.
