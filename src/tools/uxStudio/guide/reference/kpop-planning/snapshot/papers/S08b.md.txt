# S08b · 라이브 확장 데이터 — 상품 · 보상 · 친구가 늘어도 표 모양은 그대로 (이식)

**이 문서는** 라이브 확장 데이터의 당시 이식 계획과 현재 보상 표·소비 경로의 부분 구현을 나눠 읽는 시스템 기획서입니다.

**보는 법** 목차 → 간략 → 세부의 보상 묶음·뽑기 → 유저·친구 자리와 기간 칸 → 아직 안 한 것 순서로 읽습니다. 당시 출처·절 표기와 문서 정보는 하단 기록에 보존합니다. 이 문서 자체의 시뮬레이터는 없습니다.

**지금 상태** 공용 보상 표와 카드팩·상품 일부의 소비 코드가 있습니다. 원계획 전체·중첩·서버 연결은 별도이며 실제 지급·저장은 확인 대기입니다.

## 간략

**머리표** 시스템 기획 · S08b · 표 구조 · 모노 69 라이브 확장 데이터 초안 이식 · [S08](S08_표구조_연결지도.md)의 짝

**제목** 라이브 확장 데이터 — 새 상품은 새 줄로, 보상은 묶음 번호로

**훅** 「패키지면 if」를 하나 넣는 순간, 다음 이벤트마다 코드를 고쳐야 한다.

**두 줄 요약**
- **당시 설계 범위:** 라이브 서비스 중에 상품 · 뽑기 · 패키지 · 친구 기능이 늘어도 **표 모양이 안 부서지게** 원칙 여섯(E1–E6)과 표 자리 · 연결 열쇠만 먼저 잡는다. 구현은 하지 않는다. 현재의 공용 보상 표와 일부 소비 경로는 아래에서 별도로 구분한다.
- **당시 관측:** 케이팝은 지금 보상이 표마다 따로 들어 있다(마일스톤 · 카드 수집 · 덤 · 이벤트 계획). 모노 「보상 묶음」 문법으로 모을지는 **확인 필요 · 보류**. 현재는 마일스톤·수집 보상·상품 일부가 `reward_group`을 읽고, 덤 보상은 기존 칸을 직접 읽는다.

```mermaid
flowchart LR
  P[상품 · 미션 · 이벤트 보상 줄] -->|grant_bundle_id| G[보상 묶음<br/>grant_bundle]
  G --> L[묶음 줄<br/>주사위 · 루비 · 돈 % · 카드팩]
  L -->|pack 줄이면| R[뽑기 풀<br/>card_pack 확률]
  U[유저 · 친구 자리<br/>S15] -.->|id로만| P
```

이 그림은 당시 보상 묶음 설계안이다. `grant_bundle`의 명칭·중첩 계획과 현재 `reward_group`이 같은 구현 계약이라는 뜻은 아니다.

1. **늘린다** — 새 종류는 새 줄 + `type` 값. 칸 · 코드 분기를 늘리지 않는다.
2. **묶는다** — 보상은 「루비 100」이 아니라 「묶음 번호」로 준다.
3. **겹친다** — 패키지 안 상자, 상자 안 카드팩. 깊이 상한만 둔다.
4. **나눈다** — 보이는 글 · 아이콘과 실제 지급을 따로 둔다.

| 왜 지금 | 이게 핵심 | 이게 아닌 것 |
|---|---|---|
| S07b 상점 · S11 미션 · S13 이벤트가 모두 보상을 주는데, 주는 문법이 표마다 다르다(2차 5단계) | 새 줄로 늘림 · 보상 묶음 · 표시와 지급 나눔 · 서버가 진실 | 지금 표를 고치는 작업 · 결제 구현 · 친구 기능 구현 |

### 0. 한 줄 (이식)
라이브 확장 데이터는 **새 상품 · 새 보상 · 새 친구 기능이 와도 표 칸과 코드 분기를 늘리지 않게 하는 표 모양 약속**이다.

### 3. 보상 묶음 · 뽑기

**3-1. 표 자리** (이식 · 표 없음 · 키만)

아래 키 표는 당시 초안이다. ‘표 없음·키만’과 ‘모노 실제’는 그 이식 기록의 범위이며 현재 공용 보상 표의 부재를 뜻하지 않는다.

| 표 | 칸(키만) | 하는 일 | 모노 실제 |
|---|---|---|---|
| `grant_bundle` | `bundle_id` · `name_ko` · `depth_max`(겹침 상한) | 보상 묶음 머리 | 없음(초안) |
| `grant_bundle_line` | `line_id` · `bundle_id` · `line_order` · `grant_kind`(`dice` · `gem` · `money_pct` · `card_pack` · `bundle`) · `grant_ref` · `grant_amount` | 묶음 안 줄 · `bundle`이면 다른 묶음을 가리킴(겹침) | 비슷한 표 둘: `shop_bundle_line_config` · `adventure_reward_bundle`(같은 칸 `bundle_id, line_order, grant_type, grant_id, grant_amount`) |
| `card_pack_odds` | `pack_id` · `rarity` · `weight` · `guarantee` | 카드팩 뽑기 확률 · 보장 | 있음 `card_pack_odds` · `shop_random_pack_config` → 케이팝 카드 표 보류(S07) |
| `gacha_pity` | — | 천장(선택) | 없음 · 뺌(확인 필요) |

현재 공용 표는 `reward_group`(PK `reward_group_id`)과 `reward_group_entry`(PK `reward_group_entry_id`)다. 항목의 `reward_group_id`는 그룹을 직접 잇는다. `reward_kind=currency`이면 `reward_ref_id`가 통화 ID, `card_pack`이면 `item_master_id`를 가리키므로 초안의 `grant_kind`와 구분한다.

수집 보상은 `card_collection_reward.reward_group_id`를 직접 참조하고, 마일스톤·상품은 그룹의 `reward_group_type`과 `source_id`로 역조회한다. 그룹·항목을 읽는 함수의 그룹 존재·수치 검사는 모든 참조 대상과 유일성·원표 전체의 FK 성공을 보증하지 않는다. 예전 선택 관계 검사를 전수 FK나 마스터 이전 완료로 읽지 않는다.

현재 카드팩은 `item_master_card_pack.item_master_id`, 확률 줄은 `card_pack_odds.odds_id`가 식별자이며 `pack_id`가 팩을 가리킨다. 별은 `star_grade`, 보장값은 팩의 `guarantee_star`에서 읽는 부분 구현이다. 팩별 가중 추첨·마지막 장 보장과 범용 `rewardpack`·`gacha_pool`·누적 천장 `gacha_pity`는 같은 기능이 아니며 후자의 전체 계약은 미확인이다.

- 돈은 S 대비 %(`money_pct`)로만 적는다(S02 R-S02-15). 주사위는 개수. (신규) 이는 S 대비 비율로 비교하는 원계획이다. 현재 `currency` 참조의 돈 비율 항목과 실제 지급 계산·운영 정산·저장 검수는 별도로 확인한다.
- 겹침 상한 `depth_max`: 모노 69는 「상한만 둔다」고 숫자가 없다 → **값 미정** · 확인 필요. (이식) 현재 확인한 공용 resolver는 평면 항목만 소비한다. `bundle` 재귀나 상한이 구현됐다는 뜻이 아니며 비어 있지 않은 `grant_mode`·`weight`는 미지원으로 멈춘다.

**3-2. 당시 케이팝 보상 표 → 묶음 전환 계획과 현재 부분 이관** (신규)

| 당시 표 | 당시 보상 칸과 현재 구조 | 전환 계획과 현재 연결 |
|---|---|---|
| `fan_milestone_reward` | 당시 `reward_money_pct` · `reward_dice`. 현재 이 칸 대신 문턱을 두고 보상은 공용 묶음에서 읽음 | `grant_bundle_id` 한 칸은 당시 계획. 현재 `reward_group_type=fan_milestone`과 `source_id`로 역조회 |
| `card_collection_reward` | 당시 `reward_dice` · `pack_tier`. 현재 `reward_group_id`와 문턱을 사용 | 같음은 당시 전환 계획. 현재 그룹 ID 직접 참조·팩 정보는 팩 마스터에서 읽음 |
| `bonus_reward_pool` | `reward_kind` · `amount` · `mult_apply`는 현재도 직접 읽는 칸 | 풀 가중치는 남기고 보상만 묶음으로는 당시 계획. 현재 종류·수량·배수·가중치를 직접 읽는 경로 유지 |
| `tool_event_pack_reward_plan` | `dice` · `money_pct` · `token` · `pack_tier` · `pack_qty`는 당시 계획 툴 칸 | 계획 툴 표라 그대로 두고 게임 표만이라는 원계획 유지. 이번 해당 원표의 현재 연결은 미확인 |
| `shop_sku`(S07b · 키만)은 당시 이름. 현재 `item_master_shop_sku` | 당시 `grant_kind` · `grant_amount` · `pack_id`. 현재 상품 표시·종류와 보상 수량 분리 | 상품 줄 → `grant_bundle_id`는 당시 계획. 현재 상품 ID로 보상 그룹을 역조회하고 가격은 비용 경로에서 읽음 |

- **당시 이행 보류:** 바꾸는 작업은 **하지 않는다**(값 · 검사기 · 시뮬이 다 걸림). 바꿀지 · 언제 바꿀지 — 확인 필요 · 보류(유르넷 · 비앙카). (신규) 현재 일부 연결이 있어도 잔여 전환·통합 문법을 새로 확정하지 않는다. 이 문서 보완은 원표·값·검사기·코드를 바꾸지 않는다.

**3-3. 묶음 예(값 아님 · 모양만)** (이식)
모노 스타터 패키지 = 루비 500 + 주사위 50 + 상자 1. 케이팝으로 옮기면 루비 500(루비 값 같음 · ₩12) · 주사위 21(× 5/12) · 카드팩 1 — 묶음 하나에 줄 셋. 실제 상품 값은 S07b · S13a에서 정한다.

이 예는 당시 문법 설명이며 현행 가격·환산비·지급값을 확정하지 않는다. 현재 상점의 표시 글은 상품 표에서, 보상 양은 묶음에서 읽고 구매 함수는 지갑·팩 상태를 갱신해 반환한다. 그 반환이나 화면 문구만으로 실결제·서버 저장·운영 지급 완료를 판단하지 않는다.

### 4. 유저 · 친구 자리
모두 **초안 이름 · 확인 필요 · 보류**. 구조는 [S15](S15_소셜친구.md).

아래 자리·이름·제외 방향은 당시 초안이다. [S15](S15_소셜친구.md)와 친구 원문을 새로 대조한 것은 아니며, 기존 친구 검토의 [P205 상세 제안](../기획서/산출_기획서_친구매칭_제안_v1_클로드.md)·[P216 대표 요약](../개발진행기획_v01/콘텐츠별_v03/친구매칭_핵심제안서.md)을 참고한다. 제안·LOCAL 부분 상태 함수·독립 메모리 시안은 있으나 실제 호출자·서버·운영 저장 연결은 미확인이라는 경계를 재사용한다. 표의 ‘없음/자리만’을 현재 전체 기획·코드 부재나 새 정책 승인으로 읽지 않는다.

### 5. 기간 칸 — 판 · 날짜 → 시즌 일차

| 모노 | 케이팝 | 표시 |
