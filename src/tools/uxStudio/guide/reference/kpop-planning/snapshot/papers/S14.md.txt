# S14 · 구현 구조 — 층을 나누고, 표로 정하고, 가볍게 내보낸다 (이식)

**이 문서는** 층 분리·장면·표·포장에 관한 이식 규약과 현재 케이팝 코드에서 확인한 구조의 범위를 구분하는 시스템 기획입니다.

**보는 법** 간략 → 세부0~6절의 규약 → 7절의 현재 대조 → 8·9절의 범위와 확인 대기 순서로 읽습니다. 이식 목표와 현재 코드 관측을 같은 구현 상태로 합치지 않습니다.

**지금 상태** 제안(검수 대기)입니다. port 장면·등록형 시뮬레이터·공통 표 로더·별도 샌드박스 포장 스크립트의 부분 코드는 확인했습니다. 전체 층 의존, PWA·앱 포장·건강 기준 자동 차단의 연결과 실제 빌드·게임·저장·성능은 이번 범위에서 미검수입니다.

> 근거는 모노 `43_TECH_ARCHITECTURE` · `51_BUILD_ARCHITECTURE` · `53_SCENE_MODULE_ARCHITECTURE` · `57_SANDBOX_BUILD` · `118_CLIENT_HEALTH_ASSESSMENT` · `137_FX_RESOURCE_PIPELINE`(읽기만) · 케이팝 `package.json` · `vite.config` · `src/` · 현중 결정만. 값은 「(이식) 임시 시안」과 근거를 같이 적는다.

## 간략

**머리표** 시스템 기획 · S14 · 구현 구조 · 모노 43 · 51 · 53 · 57 · 118(클라이언트) · 137 이식

**제목** 구현 구조 — 여럿이 이어 받아도 안 막히는 코드 모양

**훅** 화면은 규칙을 모르고, 규칙은 화면을 모른다. 둘 사이에는 「일이 일어났다」는 소식만 오간다.

**두 줄 요약**
- 웹 하나로 만들어 모바일까지(Vite 정적 빌드 → PWA → 앱 포장). 바깥 화면은 DOM/CSS, 무대만 Three.js. 규칙은 순수 TypeScript, 값은 CSV.
- 층(규칙 · 화면 · 무대 · 흐름 · 장면)은 한 방향으로만 의존하고, 내보내기는 `index.html`이 든 zip 하나 · 용량 · 프레임 기준을 넘으면 막는다.

```mermaid
flowchart LR
  D[data<br/>CSV] --> C[core 규칙<br/>순수 TS]
  C -->|소식| B((bus))
  B --> U[ui<br/>DOM/CSS]
  B --> S[stage<br/>Three.js 무대]
  F[flow<br/>칸 흐름] --> C
  F --> U
  SC[scenes<br/>로비 · 인게임] --> F
  M[main.ts<br/>조립] --> SC
```

1. **값** — 숫자 · 글자는 CSV(`data/`). 코드에 박지 않는다.
2. **규칙** — 순수 TS가 계산하고 「일어났다」 소식만 낸다.
3. **보여 줌** — 화면(DOM)과 무대(Three)는 소식을 듣고 그린다. 서로 모른다.
4. **내보냄** — 빌드 → `index.html`이 맨 위인 zip → 용량 · 프레임 검사.

| 왜 지금 | 이게 핵심 | 이게 아닌 것 |
|---|---|---|
| 클로드 · 안티그래비티 · 커서가 같은 코드를 이어 받는데, 층 · 빌드 약속이 문서에 없다(2차 5단계) | 한 방향 의존 · 표가 원본 · 장면 교체 · zip 맨 위 `index.html` · 건강 기준 | 지금 코드를 고치는 작업 · 전투 엔진 · 서버 구조 |

### 5. 클라이언트 건강 기준 (이식)

빌드할 때마다 검사한다. 기준 숫자는 이 표가 원본이고 검사 스크립트는 판정만 한다. **CRIT 1건이면 배포를 막는다** · WARN은 적고 진행. (모노 118)

| # | 항목 | 기준 | 등급 |
|:---:|---|---|:---:|
| C1 | 첫 로딩 JS(gzip) | 3MB 이하 | CRIT |
| C2 | 첫 로딩 CSS(gzip) | 0.5MB 이하 | WARN |
| C3 | 배포 결과 전체 | 120MB 이하 | CRIT |
| C4 | 조각 하나(원본) | 8MB 이하 | CRIT |
| C5 | 배포 그림 총량 | 20MB 아래 | WARN |
| C6 | 개발 툴 배포 | 0개 | WARN |
| C7 | 외부 CDN | 없음(글꼴은 로컬로) | WARN |
| C8 | JS 메모리 | 250MB 이하 | CRIT |
| C9 | 로비 가만히 FPS | 45 이상 | WARN |

- 값은 모두 단위가 같아(MB · fps) 환산 없이 옮긴다 · **(이식) 임시 시안**. 케이팝은 그림 · 캐릭터 양이 다르니 첫 빌드 뒤 다시 본다. (이식)
- 첫 들어오기: 보통 안드로이드 · LTE에서 10초 안. 손 점검: 5분 플레이 뒤 메모리 · 로비 ↔ 인게임 10번 왕복 뒤 메모리가 계속 오르지 않기 · 가만히 10초 FPS. (이식)
- 그림 픽셀 상한: 아이콘 256 · 이펙트 가루 256 · 움직이는 UI 1024(256 금지) · 일반 그림 1024 · 캐릭터 시트는 손대지 않음. (이식)
- 끊김 원인 셋: 작은 그림을 크게 늘림 · `left`/`width`로 움직임 · `setTimeout`/`setInterval` 시계. → UI 움직임은 `transform`만 · UI 박자는 rAF 하나 · 무대 캔버스에 CSS `filter` · `backdrop-filter` 금지. (이식)

### 7. 케이팝 지금과 다른 곳 (신규)

아래는 현재 소스를 정적으로 대조해 확인한 코드 배치입니다. 앞 절의 이식 목표와 구별하며, 코드·명령의 존재를 전체 구현·실행·배포 완료로 보지 않습니다.

| 항목 | 현재 원본에서 확인한 범위 | 구분·미검수 |
|---|---|---|

## 회의록 10/16 반영 — 아트·그래픽·춤 모션·외부 연동 (신규)

> 출처: 회의록 정리 20261016_0930(콘텐츠별 핵심 문장). 받아쓰기 원문이라 표현이 거칠 수 있음. 「미정」은 현중 결정 대기. 2026-10-16 이스라트 반영. 기존 본문에 없던 문장만 옮겼다.

### 1. 일러스트·카드 이미지
- 일러스트 외주는 카드 1장 50~70만 원, 100장 약 5~6천만 원, 6개월로 부담. AI로 반값 가능하다는 의견.
- 카드는 2D 이미지 스케일업, 3D는 페스티벌 춤 영상에 쓴다.
- 남성 유저용 8등신 여캐, 여성 유저용 남캐 일러스트는 시장성 보고 결정 → **미정**.
- AI 고퀄 일러스트를 먼저 보여 주고 게임 모델을 나중에 보여 주는 기대치 관리. 완성 모델을 업스케일해 일러스트와 맞추는 방법도 있다.

### 2. 3D 캐릭터·건물
- 진짜 복셀은 AI로 뽑기 어렵다. 「복셀인 척」 해도 되지만 파츠 교체는 돼야 한다.
- 건물은 AI로 잘 나온다. 문제는 캐릭터 퀄리티: 예쁨 + 확실한 정체성.
- 참고: 홀로라이브·니지산지 SD 캐릭터. 레고·나노블록 콜라보 아이디어.
- 리깅·애니까지 되는 캐릭터는 R&D가 필요하니 기간을 길게 잡는다.
- 2D 8방향은 됐지만 캐릭터 하나 용량이 너무 커서 한계. 블렌더 사용.
- 복셀 셰이더 삼각형 약 10만 개 → 최적화 후 약 8~9천 개.
- 복셀은 모바일에서 무겁고 조합도 힘들어 큐브 스타일 저폴리곤으로 간다(네모네모한 느낌 유지).
- 캐릭터는 머리, 안경, 백팩, 마이크 같은 꾸밈과 표정 변화까지 된다. 연습생 때 트레이닝복, 그 뒤 무대복.
- 최종 건물은 2,000 폴리곤 미만.

### 3. 춤 모션·뮤비
- 2~3등신이라 격한 춤 동작은 머리가 걸려 어렵다.
- 유료 모션 구매보다 모션 캡처·영상 캡처로 직접 기본 동작을 만들고 조합하는 방식부터 테스트.
- 뮤비는 노래 파트마다 한 명을 클로즈업하는 카메라 구도.
- 오디션 선택에 애니가 「아주 많이」 들어가야 한다.

### 4. 방향 논의
- 「게임이 재밌으면 1천 명에서 시작하지만 그래픽이 좋으면 1만 명에서 시작한다」 vs 「게임만 재밌으면 된다」. 연출이 중요하다는 데는 공통.
- 지금은 「재료 준비 기간」이라 디테일보다 큰 틀.

### 5. 외부 연동
- 로그인·소셜 연동·결제(스트라이프·구글·애플)는 시드라 쪽을 쓴다.
