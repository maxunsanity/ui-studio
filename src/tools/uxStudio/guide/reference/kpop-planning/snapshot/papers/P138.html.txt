<ul>
<li>현재 디펜스의 <code>rooms</code>는 도시 건물 행에서 만들지만 시설 단계는 받지 않습니다. <code>siteOf(room)</code>도 위치·폭·깊이·높이만 넘깁니다. 세션의 내구도는 <code>rule.durability</code> 한 값입니다(<code>src/ui/bad-energy-v06/preview.mjs</code>의 rooms/siteOf/createSession, <code>src/game/bad-energy-v05/engine.mjs</code>의 createSession).</li>
<li>실제 보드 경제는 이미 <code>EconomyState.levels[tileId]</code>를 저장하고 <code>upgradeFacility</code>가 단계·비용·팬을 한 번에 처리합니다(<code>src/game/economy/session.ts</code>). 그 값을 디펜스가 읽는 연결부가 없습니다.</li>
<li>현재 원형 옥상 출발점과 길목 가드점이 혼용됩니다. 홈 자리/전투 자리를 나누는 설계는 몬스 배치 기획서를 따릅니다.</li>
<li><code>geometry.json</code>의 현재 대상5곳은 본관1채 기준입니다. city02는25×17×14m 본관 경계가 있고, 새 부속을 안전하게 넣을 명시적 대지 경계는 없습니다. 현재 좌표에 부속 둘을 임의로 붙여도 안전하다고 주장할 수 없습니다.</li>
<li>현재 보스에는70%/35%에서 바뀌는3페이즈와 세 공격 모듈이 있습니다. 새 요구는3칸 체력 구간과 전환 신호를 명료하게 만들고 몬스 디버프까지 연결하는 보완입니다.</li>
</ul>
<h2>3. 단일 입력: 시설 방어 스냅샷</h2>
<p>새 <code>facility-defense-adapter</code>는 검증된 보드 상태를 읽어 전투 시작 시 고정한 입력 하나를 만듭니다. 화면 글자를 읽거나 사본 단계 변수를 또 저장하지 않습니다.</p>
<pre><code class="language-json">{
  "schemaVersion": 1,
  "source": "economy",
  "sourceStateVersion": 6,
  "sourceFingerprint": "보드 상태의 fingerprint",
  "sourceSeason": 1,
  "sourceSeq": 123,
  "tileId": "board_tile_02",
  "cityId": "city_02",
  "facilityId": "facility_dance",
  "facilityLevel": 3,
  "compoundLayoutId": "authoring 후 확정",
  "defenseProfileId": "시안 프로필 ID",
  "tableVersion": "기획표 버전"
}
</code></pre>
<p>위 JSON은 인터페이스 예시이며 실제 저장본이나 이미 구현한 API가 아닙니다. <code>sourceStateVersion=6</code>은 현재 EconomyState 형식의 관찰값입니다. 구현 때 실제 형식과 명시적으로 맞춥니다. <code>sourceSeq</code>는 변경 추적 기준이고 새 지갑/별도 결제나 신규 재화가 아닙니다.</p>
<p>결합 순서: <code>levels[tileId]</code> → 현재 보드의 <code>map_node_id</code>/시설 ID → <code>facility_defense_profile</code>의 defenseProfile↔compoundProfile 연결 → <code>facility_defense_level</code> → 해금된 <code>compound_slot</code> → 검증된 배치/전투 스냅샷. 현재 시뮬의 댄스 시설 연결은 board_tile02/04/22/24/25↔city02/04/22/24/25이며 원본 표에 시안 상태가 표시돼 있습니다. 이를 전 세계 시설 배정 확정이라고 해석하지 않습니다.</p>

<h2>5. 건물별 상태·표적·피해 계약</h2>
<p><code>compoundSnapshot.buildings</code>는 고정 배치 정의이며, 세션의 <code>buildingStates</code>가 실제 상태를 가진다. 예시: <code>{buildingId,slotId,maxHp,hp,alive,destroyedAt,shield,weaponIds}</code>. <code>buildingId</code>는 판 안의 고유 ID이고 <code>slotId</code>는 표의 main/annex_a/annex_b 참조다. 같은 필드를 서로 대신 쓰지 않는다. 권위 HP 필드는 <code>hp/maxHp</code>이며 문장의 현재HP는 hp를 뜻한다. <code>currentHp/currentHP/durability</code>를 새 런타임에 중복 보관하지 않는다. 표의 <code>compound_slot</code>은 <code>(profile_id,slot_id)</code>가 주키이고 하위 FK는 <code>(compound_profile_id,building_slot_id)</code> 둘을 포함한다. 방어 프로필과 배치 프로필은 <code>facility_defense_profile.csv</code>에서 명시적으로 연결한다. 이전 단일건물 호환 모드에서만 legacy durability 투영을 허용하며 새 모드의 권위 상태를 두 개 만들지 않는다.</p>
<ul>
<li>피해 명령 <code>damageBuilding({battleId,actorId,damageEventId,castId,shotIndex,hitIndex,buildingId,rawDamage})</code>는 해당 건물 보호막을 먼저 차감하고 해당 HP에만 적용한다. 반환은 buildingId/rawDamage/absorbedDamage/damage/remainingHp/destroyed다. 피해 발행자가 근접 공격까지 castId/shotIndex/hitIndex를 부여하고 <code>damageEventId=battleId+actorId+castId+shotIndex+hitIndex</code>를 만든다. 수신기가 시간/좌표로 임의 ID를 추측하지 않는다. 동일 damageEventId 중복 적용0, 사망 이벤트1회, 다른 건물HP 불변을 보장한다.</li>
<li>파괴된 건물의 보석 공격·새 준비·미발사 예약·유효 홈을 중단한다. 이미 비행 중인 아군 탄은 기존 탄 정책대로 처리하며 피해를 되감지 않는다. 잔해 footprint 유지가 우선 제안이며 실제 자산 검증 전에 collider 제거를 확정하지 않는다.</li>
<li>전체 내구도 합은 분석용 <code>sumMaxHp/sumHp</code>로만 계산한다. HUD나 밸런스 비교에서 쓰더라도 실제 공동 피해 풀이 아니다. 건물별 이름·HP·파괴 표시를 유지한다.</li>
<li><code>groundAttackPathsByBuilding[buildingId]</code>, <code>airApproachByBuilding[buildingId]</code>, gem/home/return 참조를 같은 geometry revision에서 저작한다. 진지 전체 bounds는 카메라·탐색 범위일 뿐 세 건물 사이 빈 공간을 가상의 공동 피격벽으로 만들지 않는다.</li>
</ul>
<h3>악귀 공격 대상 분산</h3>
<p>일반 악귀는 진입 때 <code>targetBuildingId</code>를 받는다. 후보는 살아 있고 해당 지상/공중 경로로 접근 가능한 건물이다. 접근 비용·이미 배정된 공격자/예정 피해·건물별 목표 압력·현재 표적 유지 보너스를 표의 가중치로 계산한다. HP가 가장 낮은 건물에 항상 몰리는 규칙은 기본으로 넣지 않는다. 동점은 결정적 순번으로 풀고 표적 최소 유지 시간 동안 잠근다. 파괴·도달 불가·유효성 상실은 즉시 재계획 사유이며, 단순 거리 우열 변화는 재평가 간격/개선 문턱을 모두 넘을 때만 변경한다.</p>
<p>세 건물에 같은 무리가 복제되는 것이 아니다. 기존 출현 개체를 나누며 실제 동시 출현 길목 상한은 계속 쉬움1/일반2/도전3이다. 한 길목의 여러 악귀도 도달 가능한 서로 다른 건물에 배정될 수 있다. 보스 focus/pulse는 시전별 생존 건물을 순환하고 burst는 기존 총발수를 생존 건물에 분배하는 기획이다. 보스 총발수·총피해를 건물 수만큼 곱하지 않는다. 이미 날아간 탄은 원래 좌표를 유지하고, 미발사분의 다른 건물 재조준은 새 예고를 거친다.</p>
<h3>아군 몬스의 방어 담당</h3>
<p>몬스의 <code>defendBuildingId</code>는 악귀의 <code>targetBuildingId</code>와 연결한다. 몬스 수가 살아 있는 건물 수 이상이면 각 건물에 최소 한 명을 우선 배정하고 추가 인원은 실제 위협·층 적합·이동 비용으로 나눈다. 5명이면 무조건2·2·1이라는 고정표는 사용하지 않는다. 수가 부족하면 미담당 건물을 명시하며 보석의 피해를 숨게 올리지 않는다. 담당 유지 시간/변경 문턱은 데이터이며 건물 파괴·긴급 침투 때만 우선 재배정한다. 피니시 중에는 재배정 요청을 보류하고 실제 복귀 뒤 살아 있는 목적지와 안전 경로를 재검사한다.</p>
<h3>보호막·판정·밸런스 경계</h3>
<p>팀 피니시는 기존처럼 한 번 발동하고 한 쿨타임을 가진다. 시작 시 대상 buildingId/해당 maxHp/기존 비율을 스냅샷하고 효과 발생 시 살아 있는 대상을 재검사한다. 준비 중 파괴된 대상 몫은 폐기하며 다른 건물 이전·새 대상 추가·이미 쓴 시전 환불은 없다. 보호막의 기존 최대내구도 비례식은 유지하되 각 살아 있는 건물의 <code>maxHp × 기존 비율</code>만 배분한다. 시전 총용량은 그 합이며, 각 건물에 전체 합을 다시 주어3배로 복제하지 않는다. 건물별 흡수량을 따로 계산하고 시간으로 자동 소멸시키지 않는다. 파괴된 건물의 잔여 보호막은 폐기하고 다른 건물에 공짜 이전하지 않는 안을 제안한다. 재시전은 기존 갱신 규칙을 참조하고 누적 상한이 암묵적으로 늘지 않게 검사한다.</p>
<p>기존1200은 현재 단일시설의 사실값이다. 이를 본관과 두 부속에 각각 복사해 총3600으로 만드는 방식이나 본관HP를 나중에 깎아 부속에 나누는 방식은 채택하지 않는다. 새 <code>facility_defense_level.csv</code>는 <code>(profile_id,level,building_slot_id)</code>별 활성23행으로 본관/부속HP·보석예산을 분리한다. 각 건물의 성장HP는 감소하지 않고 해금 때 양수HP를 추가한다. 최종 사용자 규칙은 본관 파괴 패배이다. 이 규칙에 맞춘 건물별 HP·무기23행 시안은 건물 성장 문서와 기획표를 따른다. 숫자는 기획 제안이며 게임 전투/승률 검증값이 아니다. 부지·소켓·경로가 미저작인 기획표는 runtime_loadable=false이며 실행 데이터로 거부한다.</p>
<p>확정한 패배 기준은 <strong>본관 HP가0이면 패배</strong>이다. 부속 HP0은 그 건물의 보석·보호막·홈/새 발사를 정리하고 악귀/몬스 배정을 갱신하되 본관이 살아 있으면 전투를 계속한다. 새 <code>objective_policy.csv</code>의 main_slot_id를 compound profile 안에서 한 번만 해석한다. 본관이 누락/중복이면 시작 전 데이터 오류이며 다른 부속을 조용히 본관으로 대체하지 않는다.</p>
<p>매 tick의 결과 계약은 피해 적용→개별 파괴 반영→본관 HP0 패배 판정→본관 생존 시 모든 실제/예약된 적 정리 여부 승리 판정이다. 같은 tick에서 마지막 악귀와 본관이 함께0이면 패배가 우선한다. 본관 파괴 직후 새 발사·디버프·추가 보스 출현·타깃 재지정은 중단하고 이미 확정한 처치 기록/보상은 한 번만 결과에 보존한다. 240초가 지나도 미출현 잔여 보스·호위 예외가 남아 있으면 승리하지 않는 기존 조건을 유지한다. 현재 단일내구도 엔진도 engine.mjs:758–759에서 내구도0 패배를 전멸 승리보다 먼저 검사한다. 이 우선순위는 유지하되 새 buildingId별 경로와 동시 파괴·예약은 구현 후 검사한다.</p>
<p>결과에는 mainDestroyed/annexDestroyedIds/buildingResults를 분리한다. 현재 검토판의 <code>preview.mjs:699–705</code>는 패배 시 room.broken을 켜고 수리비를 기본800×패배비율0.5=400으로 정하며 resultApplied로 중복 적용을 막는다. <code>preview.mjs:274–279</code>의 보드 수리는 현재 돈을 한 번 차감하고760ms 뒤 정상 상태로 돌린다. 이 값은 v01/rule.csv의 기존 설정을 읽는 사실이며 새 부속 수리 가격을 제안한 것이 아니다. 본관 패배만 이 기존 시설1건 broken에 투영하고 부속 손실은 battleResults에만 기록하는 설계안이다. 기존 finish/resultApplied의 결과1회 가드를 유지한다.</p>
<p>현재 검토판 G.money/room.broken은 메모리 상태이며 <code>serialize():904</code>는 repairCost·할인 사유·진행 전투를 복원하지 않는다. 이를 실제 경제 영구저장이 완성된 상태로 설명하지 않는다. 실제 게임 연결에서는 기존 경제 상태 API와 시설 파괴/수리 저장 지원 여부를 확인한 뒤 결과 어댑터를 구현하고, 판별 결과ID·할인 사유·1회 차감/수리 범위까지 명시적으로 저장/복구해야 한다. 영구 시설 성장 레벨과 전투 임시HP를 혼합하지 않는다. 전투 도중 재개 기능을 만들 때는 개별 파괴를 그대로 복원하고, 새 전투 초기화와 혼동해 부속을 부활시키지 않는다. 독립HP·분산 타깃으로 난이도가 달라지는 범위를 별도 계측하며 악귀HP를 조용히 줄여 상쇄하지 않는다.</p>
<p>본관만 있는 L1이 패배하면 살아 있는 건물 home이0개다. 최종 몬스 복귀는 전투 home과 분리한 <code>compoundSnapshot.resultReturnAnchor</code>(건물 밖 검증된 집결/아이돌 복귀 접속점)를 사용한다. 위치는 저작 입력이며 새 좌표를 추측하지 않는다. 종결 뒤에는 전투 배정 복구보다 결과 복귀가 우선이고 파괴된 지붕으로 도킹하지 않는다.</p>
<h3>개별HP의 화면 표현 제안</h3>
<p>상단 보호시설 패널에는 본관 이름·HP를 주표시로 두고, 부속A/B는 작은 개별HP 칩과 보석 작동 상태를 함께 둔다. 잠긴 부속은 해당 단계에서만 해금 안내로 구분한다. 월드의 건물HP는 피격 중/선택 중 필요한 대상에 표시하고, 파괴된 부속은 파괴 아이콘과 ‘보석 지원 중단’으로 남긴다. 본관이 남아 있는데 ‘패배’처럼 보이는 전체 경고를 띄우지 않는다. 모든 HP칩은 개별 buildingId를 읽고 합계막대로 대체하지 않는다.</p>
<p>보스 패널은 별도3체력 구간과 현재 페이즈를 표시한다. 경고·카드·피니시 안내의 기존 우선순위/전용 영역을 재사용하고, 세 건물 패널 때문에 선택 카드나 보스 예고가 가려지지 않게 웹/세로/가로에서 검수한다. 크기·색·시간·문구는 presentation 데이터 참조이며 이 문서의 설명을 화면 좌표 하드코딩으로 옮기지 않는다.</p>
<h2>6. 핵심 실행 순서</h2>
<ol>
<li>검증된 시설 방어 입력을 만들고 단계·설정·해금 건물을 고정합니다.</li>
<li>부지 authoring 데이터로 합성 배치를 검증합니다. 도로/이웃 건물 침범이 있으면 그 배치를 배포 대상에서 제외하고 오류 위치를 보여 줍니다.</li>
<li>3동을 반영한 충돌체·동선·전투/홈 자리·카메라를 같은 버전으로 함께 확정합니다. 시각 건물만 늘리는 반쪽 반영을 허용하지 않습니다.</li>
<li>단계에 맞는 내구도와 몬스 수와 무관한 건물 방어체를 만듭니다. 기존 임시 roof_drone을 동시에 남겨 중복 공격하지 않습니다.</li>
<li>몬스는 주변 대기 자리에서 경계합니다. 실제 적을 감지한 뒤 준비·요격으로 이동하고, 상대가 사라지면 유지 시간/복귀 조건을 따릅니다.</li>
<li>전투 tick에서 공격 예약/상태 효과/보스 체력 구간은 명시된 우선순위로 처리하고, 화면은 발행된 전환/시전/약화/해제 이벤트를 표시합니다.</li>
<li>승패가 확정되면 새 공격·디버프 예약을 끊고 일시 효과를 해제한 뒤 안전하게 복귀합니다. 영구 시설 성장을 지우지 않습니다.</li>
</ol>
<p>발사 예약 방지 키는 <code>battleId + actorId + castId + shotIndex</code>, 실제 피해의 멱등 키는 위 <code>damageEventId</code>, 전환 이벤트는 <code>battleId + bossId + phaseNo</code>, 시설 스냅샷은 <code>fingerprint + season + tileId + sourceSeq + tableVersion</code>을 기준으로 설계합니다. 이 키들은 예시 계약이며 현재 전부 구현돼 있다는 뜻이 아닙니다.</p>
