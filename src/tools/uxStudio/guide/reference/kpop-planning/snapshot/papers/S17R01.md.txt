# 기획서 툴 구조 분리·서버 기능 검토안

- 작성: codex(단이) · 2026-11-03
- 대상: 기존 7007 기획서 툴의 문서 목록·검색·읽기·주소 관리
- 문서 상태: 현행 구현 사실과 후속 제안을 구분한 검토안. 제안은 **제안(검수 대기)**이며 도입 승인이나 구현 지시를 뜻하지 않는다.
- 결론: 문서 기능을 4개 모듈로 분리한 현행 코드를 유지한다. **이번 TanStack Start 도입은 0**이다. 원본 저장 등 서버에서 처리할 기능이 실제 요구로 확정되면, 외곽 화면·경로 관리와 명시적인 서버 함수만 후속 도입 범위로 검토한다.

## 1. 현행 구현 사실 — 소스 확인

한 파일에서 서로 엮여 있던 문서 기능을 아래처럼 나눴다. CSV 로더와 MD 원본, 게임·발란스 실행기, 기존 7007 진입 주소는 유지한다. `main.ts`는 기능을 연결하는 외곽 코드로 남으며, 전체 앱의 상태가 모두 분리된 단계는 아니다.

| 구분 | 실제 파일·주요 함수 | 맡은 일 | 외부에 남긴 일 |
| --- | --- | --- | --- |
| 문서 조회·검색·정렬 | `src/tools/planningDocs/document-catalog.ts:16` · `findDocument`, `matchesDocument`, `sortDocuments` | 문서 번호/경로 조회, 제목·별칭·요약·분류 이름 검색, 기존 정렬·보관 구분 | CSV 로딩, DOM 조작, 주소 변경 |
| 목록 표시·행동 전달 | `src/tools/planningDocs/document-list.ts:23` · `documentListHtml`, `bindDocumentList` | 콘텐츠/칸/시스템별 목록, 검색 결과, 접힘 표시, 목록 버튼 연결 | 선택 상태, 읽음 저장, 개발 화면 실행은 `main.ts` 콜백 |
| 문서 읽기·표시 | `src/tools/planningDocs/document-reader.ts:7` · `createDocumentReader`, `documentBody`, `looseDocumentHtml` | 선택 중 원문 캐시, 늦은 응답 무효화, MD 프리뷰/원본과 연결 문서 표시 | 실제 읽기는 기존 `fetchDocText` 주입, 화면·실행기 전환은 `main.ts` |
| 주소·방문 기록 | `src/tools/planningDocs/navigation.ts:19` · `createPlanningHistory`, `readPlanningQuery`, `planningQuery`, `documentHref` | 기존 query 형식, 공유 주소, 뒤로/앞으로 기록·분기·복원 | 실제 브라우저 주소·history와 화면 복원 동작은 `main.ts` |
| 조립·기존 실행기 연결 | `src/tools/planningDocs/main.ts:1` | 위 4모듈과 기존 CSV/MD/개발 목록 연결, 문서·게임·발란스 전환 | map/gap/iframe 조립과 일부 앱 상태는 계속 이 파일에 남음 |

검색 대상은 **등록표의 문서 정보**다. 이번 변경으로 MD 본문 전체 검색이나 서버 검색 인덱스를 추가하지 않았다. 기존 P73/P74/W 우선순위와 표시 상수는 이동해 보존한 것이며 새 기획·발란스 값을 정한 것이 아니다.

### 1.1 읽기 경계

`main.ts:194`에서 `createDocumentReader(fetchDocText)`로 기존 읽기 함수를 주입한다. `md.ts:295`의 `fetchDocText`는 진행 중인 같은 URL 요청을 합류시키고 `cache: "no-cache"`로 원본을 재검증한다. 문서를 새로 선택할 때 캐시를 비우는 기존 연결(`main.ts:485`, `main.ts:1153`)을 유지하며, 프리뷰/원본 전환에서는 선택 중 원문을 재사용한다.

읽기를 시작할 때 세대 번호를 받고, 다른 문서나 게임·발란스 화면으로 이동하면 번호를 갱신한다. 이전 번호의 응답은 버린다. 네트워크 요청을 반드시 취소하는 기능은 아니며, 늦게 도착한 문서가 현재 화면을 덮어쓰지 않게 하는 기능이다. 서비스 응답 뒤 실제 DOM 표시 직전에도 현재 번호를 검사한다(`document-reader.ts:16`, `main.ts:1158`, `main.ts:1255`).

### 1.2 주소·실행기 경계

7007의 기존 진입점 `/docs/planning/planning-docs-tool.html`과 query 계약을 보존한다. `face`, `doc`, `content`, `sort`, `paper`, `plan`, `deck`, `view`, `flowNode`, `flowReference`, `simulation`, `testPage`, `hubSource`는 기존 화면 문맥에 맞춰 유지한다. 브라우저 방문 기록의 `pdNav`도 유지한다(`navigation.ts:35`, `navigation.ts:49`, `navigation.ts:70`).

주소와 방문 기록 계산을 분리했으며, 실제 선택·복원·브라우저 이벤트는 `main.ts:301`, `main.ts:354`, `main.ts:426`에서 연결한다. 게임·발란스 iframe의 재사용, 숨김 시 중단 메시지, 기존 `postMessage` 계약은 외곽에 남겼다. 실행기 안쪽을 새 프레임워크로 옮기지 않았다.

### 1.3 다운로드와 원본 저장의 구분

`main.ts:933`의 `saveLinkedFile`은 파일을 읽어 Blob과 다운로드 링크로 사용자의 다운로드 폴더에 전달한다. HTML에서는 Vite가 주입한 client script를 제거하는 기존 처리를 유지한다. **프로젝트 원본을 덮어쓰는 저장 기능은 없다.** 다운로드가 가능하다는 사실을 원본 저장·버전 관리가 구현됐다는 뜻으로 쓰지 않는다.

## 3. 서버 필요 기능 — 제안(검수 대기)

현재 문서 읽기·등록표 검색·주소 공유·다운로드는 기존 Vite 읽기 경로로 처리한다. 이 범위만으로 새 원본쓰기 서버나 계정 체계가 필요하다고 판단하지 않는다. 서버 기능은 아래 조건이 실제 요구가 됐을 때 연다.

| 기능 | 현재 상태 | 서버가 필요한 조건 | 최소 처리 범위·검수 기준 |
| --- | --- | --- | --- |
| 등록표·MD 읽기, 검색, 다운로드 | 기존 기능 유지 | 현재 범위에는 새 서버 기능 요구 없음 | 기존 CSV/MD 경로, 최신 원문 재검증, 공유 주소 유지 |
| 툴 안에서 원본 저장 | 미구현 | 사용자가 허용한 기획 문서를 툴에서 고치고 프로젝트 원본에 반영하도록 요청 | 등록 문서의 텍스트 읽기·저장부터 제한. 파일 생성·삭제·이동과 CSV 구조/게임 수치 변경은 별도 범위 |
| 저장 대상 검증 | 새 쓰기 기능 없음 | 원본쓰기 도입 시 필수 | 카탈로그 ID를 서버에서 허용 경로로 해석. 허용 루트·확장자, canonical realpath·symlink 이탈 검증. 외부 URL·임의 절대경로 거부 |
| 권한·요청 출처 | 새 계정 체계 없음 | 쓰기 도입 또는 LAN/원격/다중사용자 운영 | 로컬 쓰기에도 요청 origin·허용 작업 검증. 원격/다중사용자면 서버에서 인증과 읽기/쓰기 권한 검증 |
| 동시 변경 충돌 | 원본 저장 기능 없음 | 다른 에디터·AI와 같은 원본을 저장 | 읽은 원문의 hash를 revision으로 반환. 저장 시 `expectedRevision` 비교. 다르면 원본 보존 후 충돌 응답 |
| 백업·버전·저장 실패 | 새 저장 서비스 없음 | 원본쓰기 도입 시 필수 | 원본 교체 전 시간·작성자 백업, hash·저장 시각 기록, 임시파일 후 원자적 교체. 백업/권한/충돌 실패 시 원본 유지 |
| 실시간 공동편집 | 요구 미확인 | 여러 사용자가 같은 문서를 동시에 편집하도록 직접 요구 | 충돌 검사와 구분해 별도 설계. 이번 단계에 공동편집 엔진을 추가하지 않음 |
| 서버 검색 인덱스·DB | 요구 미확인 | 현행 등록표 검색 범위를 넘는 검색/규모 요구가 확인됨 | 성능·검색 대상부터 측정하고 별도 판단. 프레임워크 도입 이유로 DB를 추가하지 않음 |

백업·버전은 기존 `문서이름.log.md`의 변경 이력 규약과 관계를 후속 설계에서 정한다. 새 이력 저장소를 먼저 만들어 중복 운영하지 않는다. 서버·프레임워크는 경로 허용, 충돌 검사, 백업 정책을 자동으로 결정해 주지 않는다.

저장 요구가 확정됐을 때의 계약 예시는 다음과 같다. 아래 이름과 필드는 **제안(검수 대기)**이며 새 endpoint나 서버 함수를 생성한 것이 아니다.

| 작업 | 입력 | 결과 |
| --- | --- | --- |
| 허용 문서 읽기 | `catalogId` | `catalogId`, `path`, `content`, `revision`, `modifiedAt` |
| 허용 문서 저장 | `catalogId`, `content`, `expectedRevision` | 성공: `revision`, `modifiedAt`, `backupRef` / 충돌: `currentRevision`과 충돌 상태 |

브라우저가 보낸 경로를 그대로 파일시스템 경로로 사용하지 않는다. 경로 결정과 검증, 파일 접근, 백업, 최종 교체는 서버의 한 저장 서비스가 맡는다. 백업 참조나 오류 응답으로 범위 밖 로컬 경로·비밀 파일 내용을 내보내지 않는다.

## 4. TanStack Start 도입 경계 — 제안(검수 대기)

### 4.1 이번 단계: 도입 0

현재 `package.json`은 Vite·TypeScript 중심이며 React/TanStack Start 의존성을 추가하지 않았다. 문서 기능의 실제 경계를 먼저 분리한 현재 구현을 기준으로 검수한다. 원본 저장·권한·여러 사용자 운영이 아직 요구로 확정되지 않은 상태에서 서버 기능을 만들지 않는다.

### 4.2 후속 도입을 검토한다면

후속 평가 범위는 **기획서 툴의 외곽 화면(shell)·경로 관리(routing)와 명시한 서버 함수**까지다. 네 모듈의 검색/읽기/주소 계약과 CSV/MD 원본을 재사용하고, 게임·발란스 실행기는 기존 iframe으로 연결한다. 서버 함수 후보는 제3절의 허용 문서 읽기·원본 저장처럼 서버 실행이 필요한 작업에만 둔다. 화면 표시나 기존 로컬 검색을 이유 없이 서버 호출로 바꾸지 않는다.

Start의 경로 관리 기반은 TanStack Router이며, Start는 서버 함수·서버 경로 등을 추가한다. 서버 기능을 쓰지 않는 경우 Router 단독도 선택지라고 공식 문서가 안내한다. 따라서 외곽 경로 정리만 필요하면 Router 단독, 명시적인 서버 기능까지 필요하면 Start, 기존 Vite와 작은 저장 서비스 유지도 비교할 수 있다. **이 선택은 현행 소스 확인에 근거한 제안(검수 대기)**다. [공식 Overview](https://tanstack.com/start/latest/docs/framework/react/overview)

Start의 서버 함수는 앱에서 호출하는 서버 전용 로직이며 클라이언트 코드에서 호출할 수 있다. 내부 파일시스템 접근은 서버 서비스로 두고 호출 경계를 명시한다. 외부 앱이 호출할 공개 API는 서버 함수와 같은 것으로 간주하지 않는다. 실제 채택 버전의 요청 출처 보호·입력 검증을 확인하고, 별도로 경로·권한·충돌·백업을 구현한다. [공식 Server Functions](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)

**SSR(서버가 화면 HTML을 먼저 만드는 방식)은 이번 요구의 필수 조건이 아니다.** 공식 SPA mode는 브라우저에서 화면을 그리면서도 서버 함수·서버 경로를 함께 쓸 수 있다고 설명한다. 저장 기능을 사용한다면 해당 요청을 실행할 서버 경로/실행 환경은 별도로 필요하다. 기존 HTML·MD·CSV·이미지 주소가 SPA shell로 잘못 넘어가지 않도록 정적 파일과 동적 요청 경계를 우선 확인해야 한다. [공식 SPA mode](https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode)

### 4.3 후속 도입의 검수 조건

1. 원본 저장 등 필요한 서버 작업과 대상 문서 범위를 먼저 확정한다.
2. 외곽·경로와 해당 서버 함수만 작은 검증 단위로 옮긴다. 새 기본 화면·게임 저장·초기화 기능을 섞지 않는다.
3. 7007 목록 → 관련 카드 → 실행 → 실제 화면 순서로 기존 진입과 공유 주소를 확인한다. 뒤로/앞으로, 연결 MD, 프리뷰/원본, 원문 최신 반영, 다운로드를 함께 확인한다.
4. 게임·발란스 iframe 재사용과 중단·재개 메시지, 늦은 문서 응답 회귀가 유지되는지 확인한다.
5. 쓰기를 넣는다면 허용 경로 이탈·충돌·백업 실패·권한 실패에서 원본이 유지되는지 확인한다. 검수 뒤 도입 여부를 결정한다.

## 5. 제품 화면 문구와 이번 산출 범위

모듈명, SSR, server function, migration 등 구현 설명은 이 검토 문서와 개발 검수 자료에 둔다. 제품 화면에는 문서 제목·검색·읽기·원본·다운로드 등 사용자의 실제 행동에 필요한 정보만 보여 준다. 이번 문서 작성에서 제품 UI 문구는 수정하지 않았다.

이번 산출은 이 MD 한 파일이다. CSV/카탈로그 목록 등록, 기획서·발란스 수치 변경, 새 서버 설치·실행, Start 설치·설정, 게임·발란스 코드 수정, 공용 STATUS·보고 갱신은 이 문서 작성 담당의 범위가 아니다. 현행 구현의 전체 검수와 공용 보고는 부모 본체가 맡는다.
