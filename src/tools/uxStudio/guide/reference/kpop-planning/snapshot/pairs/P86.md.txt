# P86 · 핵심제안 개발 기획서 작성 규칙

> **이 문서는** 모든 기획서의 공통 독서 틀과 대표 개발 기획서의 7장 순서를 정하는 작성 규칙입니다.

> **보는 법** 0장(모든 기획서의 틀) → 1~7장(대표 개발 기획서 장 순서) → 등록 절차 순서로 읽습니다. 시뮬레이터 없음.

> **지금 상태** 개발됨(기획서 툴의 핵심제안 개발 탭 · 로그 버튼 기준).

## 0. 모든 기획서의 틀 (헌법 제6장)

| 자리 | 쓰는 것 |
|---|---|
| 맨 위 세 줄 | **이 문서는**(무슨 기획서인지 한 줄) · **보는 법**(읽는 순서, 같이 열 시뮬레이터 링크 또는 「시뮬레이터 없음」) · **지금 상태**(「개발됨」 또는 「현재 개발되지 않음, 진행 중」). 표가 아니라 굵은 글자로 시작하는 세 줄로 씁니다 |
| 본문 | 사람이 처음부터 끝까지 읽을 수 있게 현재 기획과 실제 구현 범위를 구분해 씁니다. 기획에 있지만 아직 만들지 않은 항목도 이름과 제작전 상태를 남깁니다. 변경 이력 · 지시 기록 · 줄 번호 · 「검수 대기」 · 봇 이름은 쓰지 않습니다 |
| 맨 아래 접힌 칸 | 「읽은 원본」 · 「계기」 · 상태 줄 · 경로 · 줄 번호 목록 같은 짧은 작업 메모. md는 `<details><summary>작업 기록</summary> … </details>`, html은 같은 내용을 `<details>`로 |
| 로그 파일 | 같은 폴더의 `문서이름.log.md`(확장자를 떼고 `.log.md`). 안은 `## 변경 이력`(최신이 위 · `날짜 시각 · 누가 · 무엇 · 왜 · 근거`)과 `## 지난 기록`(본문에서 뺀 옛 내용을 고치지 않고 그대로). 짝 md·html은 로그 하나. 카탈로그에 등록하지 않으며, 기획서 툴이 이 파일을 찾아 「로그」 버튼을 보입니다 |
| 핵심제안 카드 개요 | `planning_development_plan.csv`의 `summary`는 1~2문장 개요만 둡니다. 현중 지시 없이 고치지 않고, 세부와 변경 내용은 기획서와 로그에만 씁니다. 날짜 · 옛 안 · 결정 내역 · 「발란스 대기」 · 「검수 대기」는 쓰지 않습니다 |
| 링크 | 다른 문서 · 개념을 가리키는 낱말(문서 번호 · 능력 · 배경 · 이야기 · 성격 · 라포 · 팬 등)마다 책갈피 대표 문서로 가는 링크를 겁니다. 주소는 그 문서 파일로 가는 상대 경로(html 짝이 있으면 html, 없으면 md. 예: `[P147](../콘텐츠별_v03/팀결성_팀스탯_기획서.html)`)로 통일합니다. 기획서 툴 자체의 화면 전환 주소는 query/hash를 보존하는 아래 예외를 따릅니다. 대표 문서가 없는 말은 보고 목록에 올립니다 |
| 책갈피 · 핵심제안 · 카드 | 책갈피가 메인입니다. 모든 내용이 책갈피에 있어야 하고, 핵심제안 개발과 제안서 카드는 책갈피와 같은 내용 · 같은 숫자(표 값)로 맞춥니다 |


### 작업 시작과 검수 순서

현재 요청과 허용 범위 → 관련 카드·원문 → 실제 원표·로더·공유 계산 → 저장을 쓰는 함수(writer)와 조회 경로를 읽습니다. 네 도구의 자세한 경계는 [S17 현재 프로젝트 예](../../시스템기획/S17_기획서툴_제작기본양식_v02.md#current-tool-boundaries) 한 곳에서 확인합니다. 구현 확인을 숫자·운영 정책의 새 승인으로 바꾸어 적지 않습니다.

백업 후 범위 안에서 수정하고, 원표·키·미정값 → 계산·상태·중복 정산·저장 범위 → 7007 목록→관련 카드→기존 버튼→실제 화면→복귀·캡처 순서로 확인합니다. 코드·계산·UI·플레이 중 확인한 범위와 남은 범위를 구분합니다. 기획·표·계산 구현·실사용·화면 연결을 각각 확인하고, 기획만 있으면 이름+제작전, 표만·계산만·연결 대기·발란스 대기·후보를 근거로 구별하며 실사용 중 「준비중」 잔류도 따로 기록합니다.

규칙·표·화면·콘텐츠 개수를 바꾸면 그 내용을 확인하는 시험(`tests/`)도 같은 작업 안에서 지금 기준으로 고치고, 고친 시험을 다시 돌려 통과를 확인합니다. 옛 규칙을 보는 시험은 지우지 않고 바뀐 근거(누가 · 언제 결정)를 시험 안에 적습니다. 시험 기대값은 표에서 읽고 숫자를 지어내지 않습니다.

### 문서 독서와 core 조작 주소

HTML 확장자만으로 기획서와 실행 툴을 구분하지 않습니다. 표준 기획서의 짝 MD·목차·하단 이력은 독서로 확인하고, core 조작은 등록된 실제 실행 주소와 모드로 확인합니다. 같은 이름의 MD가 있다는 이유만으로 옛 툴 설명서를 새 정본으로 사용하지 않습니다.

기획서 툴 자체의 동일 출처 주소 `/docs/planning/planning-docs-tool.html?face=…&doc=…&plan=…#…`는 화면 이동 계약입니다. 일반 문서 파일 링크로 치환하지 않고 원래 query와 hash를 보존합니다. 현재 소스는 이 주소를 `data-planning-view=1`로 구분해 기존 `goTool`의 같은 화면 전환으로 전달합니다. 과거의 「?doc 주소는 문서 안에서 이동하지 않는다」는 설명을 이 예외에 적용하지 않습니다. 실제 왕복은 별도 화면 검수로 확인합니다.

새 Markdown 표는 구분행의 각 칸을 `---`로 쓰고 목차 hash는 실제 렌더된 제목 ID와 대조합니다. CSV는 헤더와 각 데이터 행의 칸수·출처명 전달을 함께 확인하며, 자세한 현재 계약은 [S17의 CSV와 Markdown 읽기 계약](../../시스템기획/S17_기획서툴_제작기본양식_v02.md#3-1-csv와-markdown-읽기-계약)에서 봅니다.

### 같이 맞추는 복사 자료·카드·표 구조

- `작성규칙.html`의 `template`·`author-prompt`와 [빈 양식 MD](기획서_빈양식.md)·[AI 작성 지시](작성AI_프롬프트.md)는 같은 공통 내용으로 맞춥니다. 첫 세 단락·하단 작업 기록·짝 로그 방식이 한쪽에만 남지 않게 합니다.
- 제안 카드의 짧은 설명은 실제 `proposal-card-lobby-mock.html`의 `DECKS.copy/sub/core`에서 따로 표시됩니다. 본문·카탈로그만 고치면 이 설명도 자동으로 바뀐다고 가정하지 않습니다. `DECKS.core` 문장 배열과 자체 툴의 core URL은 다른 항목입니다.
- 표 구조 변경이 맡겨진 경우 `schema_table.csv`·`schema_column.csv`·필요한 `schema_config_key.csv`와 실제 CSV를 대조하고, 지정 생성기 후 `node scripts/schema-generate.mjs --check`를 확인합니다. 자동 생성하는 `schema.ts`·`table_registry.csv` 등을 손으로 고치지 않습니다. 보관(`archived`)·외부 경로를 현행 로더의 정본으로 새로 지정하지 않습니다.
- 포장·업로드 작업은 프로젝트의 [샌드박스 포장 규칙](../../../../../../★샌드박스_빌드_규칙.md)과 연결된 실제 포장 필터를 다시 읽고 복사본에 적용합니다. 백업·임시·협업 기록·테스트·`.git`·`node_modules` 등 제외와 필요한 의존 파일을 함께 확인하며, 시뮬레이터가 읽는 `data/game`을 통째로 빼지 않습니다. 과거 파일 수·용량 기록을 현재 서비스 한도로 새로 확정하지 않습니다.

> **첫 장 = 수정 제안서.** 대표 기획서(탭에서 처음 열리는 문서)는 언제나 **지금 제안서와 시뮬** 기준으로 씁니다. 이전 기획이 다르면 본문에 섞지 않고 로그 파일(`문서이름.log.md`)의 「지난 기록」으로 옮깁니다. 옮긴 글은 고치지 않고 그대로 둡니다.

모든 대표 기획서는 **같은 장 이름 · 같은 순서**입니다. 문서는 장 이름으로 찾기 때문에 장 이름이 같아야 합니다.

## 1. 개요


### 콘텐츠 경계

「핵심제안 시스템 개발」 탭(기획서 툴 `?face=development`)의 **대표 개발 기획서** 작성 규칙입니다. 이 탭은 바뀌어 가는 제안서(`docs/planning/proposal-concept/`)를 바탕으로 만든 개발 기획서를 담습니다. 모노 이식 결과는 책갈피 S 문서에만 두고, 이 탭 문서에서는 **링크만** 겁니다.

- 맡는 것: 장 이름·순서, 표시 말, 히스토리 처리, 등록 절차.
- 맡지 않는 것: 책갈피 S 문서 양식(헌법 제18·19조), 툴 문서(P94 · P73), 참고 자료(P95), 안내 문서(P75 · P105)의 본문 구조.

### 현재 기준과 목표

| 규칙 | 내용 |
|---|---|
| 상태 줄 | 맨 위 「지금 상태」는 **개발됨**·**현재 개발되지 않음, 진행 중**을 바탕으로 부분 구현·실제 사용·화면 연결·제작전·미검수 범위를 함께 설명합니다. 두 상태 어휘만으로 부분 상태를 지우지 않습니다. 7장 상태표의 개발 끝·개발 중·기획 중·제외와 근거를 함께 봅니다 |
| 확정 | 검토가 끝나 **툴·시뮬·코드에 들어간 것은 확정**입니다. 「확정(시뮬 v05)」처럼 근거를 붙입니다. 구현 확인 표기이며 숫자·운영 정책의 새 승인이나 현중 결정을 대신하지 않습니다. |
| 기획·구현 대조 | 현재 소스의 입력·모드·계산·실제 사용을 대조해 구현 사실을 기록합니다. 기획 목적·원결정과 표시 시안·운영을 분리하고, 불명확한 수치·의도는 억지로 맞추지 않습니다 |
| 최신 제안서 | 본문은 모두 지금 제안서 기준. 이전 기획은 히스토리로만 |
| 출처 꼬리표 | (신규) · (이식) · (합침) — 단락 · 표 줄 · 값에 붙입니다. 카탈로그 `origin`(new/port/merged)과 같은 말 |
| 결정 표시 | **확정**(근거) · **제안**(시뮬·코드에 아직 없는 숫자·문구) · **값 없음**(값이 아직 없음 · 무엇이 없는지 정확히 적음) |
| 빈 칸 | **미완**(아직 안 씀 · 이유 한 줄) · **해당 없음**(이 콘텐츠엔 필요 없음) · **미제작**(그림·모델이 없음). 장은 빼지 않습니다 |
| 실존 이름 | 실존 아이돌 · 그룹 이름 금지(헌법 제9조) |

## 3. 구동 방법·시뮬레이션

맨 위 한 줄: `화면 흐름: [들어오는 화면] → [이 화면] → [나가는 화면] · 스샷 [있는 증거] · 이식 비교 [책갈피 S]`

- 실행은 P94 공용 시뮬레이터의 모듈 링크와 새 창 링크로 엽니다. 문서 안에 시뮬레이터 iframe을 넣지 않습니다.
- 시작 · 조작 · 판정 · 결과 · 저장 · 복원 · 중단 중 **구현된 것만** 설명하고, 없으면 미구현이라 적습니다.
- 스샷은 이미 있는 증거 그림만 씁니다. 새 그림을 만들지 않습니다. 없으면 「미완」.
- 모노 · 케이팝 나란히 비교는 책갈피 S 문서에 있으므로 링크만 겁니다.
- 새 시뮬 모듈은 `data/simulator/simulator_module.csv`에 등록합니다(`simulator_module_*` · `simulator_instance_*`, 진입 파일 `mount(ctx) → activate/deactivate/serialize/dispose`). 본게임으로 옮길 계산은 `src/game`의 독립 모듈로 둡니다. 별도 시뮬레이터 페이지를 늘리지 않습니다.
- :7007 서버가 꺼져 있으면 보고하고 기다립니다.

4. **화면·연출 목록**
5. **남은 결정** — 마지막. 원문 라벨 그대로 선택지만 적습니다.

| 실제 그림 또는 「미제작」 | 역할 | 애니 · 변형 | 검증한 경로 · 키 | 있음 · 미제작 |

마지막 소제목은 **추가 제작·연출 리소스**입니다. 원본 그림 · 모델을 지우거나 덮어쓰지 않고, 새 제작물은 버전을 올립니다.

## 6. 관련 CSV·테이블 데이터

| 파일·보기 | 역할 | 주키·참조 | 값 (출처 꼬리표 · 결정 표시) | 담당 |
|---|---|---|---|---|

맨 아래 한 줄: `주사위 환산: 하루 사용 ○개 · 이 콘텐츠 지급 ○개 (60일 시뮬 링크)` — 자원을 주거나 쓰지 않는 콘텐츠는 `주사위 환산: 해당 없음`. 환산 숫자는 문서에서 새로 계산하지 않고 이식 쪽 60일 시뮬([발란스 툴](/docs/planning/balance-tool.html)) 결과만 인용합니다. 「일차」는 시뮬 · 표의 축으로만 씁니다.

- 등록된 공용 표는 `/docs/planning/game-table-tool.html?plan=콘텐츠키#table_key`로 문서 안에 보입니다.
- 미정값을 0이나 기본값으로 채우지 않습니다.

### 등록 절차

1. **문서 번호**: `data/planning_doc_catalog.csv`에서 쓰지 않은 번호를 고릅니다. 머리줄 `path,no,title_ko,aliases,content,shelf,status,pair_html,pair_tool,pair_ops,parent_constitution,one_liner,origin,work_status,evidence,value_status,system_group,dev_doc,added_on`.
2. **개발 목록**: `data/planning_development.csv`에 `planning_development_` 고유키로 1행. 기존 행 · 정렬값은 지우지 않습니다.
3. **콘텐츠**: 새 콘텐츠일 때만 `data/planning_development_plan.csv`에 1행(`root_doc_no` = 대표 문서, category = common · content · guide · todo, `is_default=1`은 전체 1건).
4. **자료 연결**: `data/planning_development_reference.csv`에 역할별 1행씩. role = root(대표) · system(관련 시스템) · resource · tool · table · csv · **history(이전 기획만)** · sample. 진행 점검 · 검수 보고는 history가 아니라 system입니다.
5. **사용 CSV**: `data/planning_csv_table.csv`에 파일 1행, `data/planning_csv_usage.csv`에 콘텐츠별 관계 1행(runtime · reference · resource). 같은 콘텐츠+CSV를 두 번 넣지 않습니다.
6. 툴 `?face=development&doc=번호&plan=콘텐츠키`에서 열림 · 미리보기 · 뒤로/앞으로를 확인합니다.

## 테이블 데이터 규칙 · 마스터 표

- 데이터 종류마다 **마스터 표**를 하나 둡니다. 모든 콘텐츠가 같은 마스터를 같이 씁니다.
  - 아이템(카드팩·상점 상품·보상·티켓·주사위·미션 보상 등) → `data/master/item_master.csv` · 종류 칸 `item_type`
  - 스킬(몬스 스킬·디펜스 스킬·아이돌 스킬) → `data/master/skill_master.csv` · `skill_type`
  - 캐릭터·NPC(후보·몬스·나쁜 기운 적 등) → `data/master/character_master.csv` · `character_type`
  - 건물 → `data/master/building_master.csv` · `building_type`
- 콘텐츠 표는 마스터 ID만 가리킵니다. 같은 것을 콘텐츠 표에 새로 정의하지 않습니다.
- 열쇠칸 값(ID)은 표 파일의 영문 이름 전체를 접두어로 씁니다(풀네임 규칙). 열 이름은 그대로 둡니다.
- 발란스 값은 코드에 쓰지 않고 CSV에 둡니다. 값이 없으면 칸을 비우고 「비어 있음(0으로 동작)」으로 적습니다(분업표 절대 원칙 ①).
- 상태 칸(`value_status`)과 화면 문구의 상태 낱말은 **확정 · 제안 · 값 없음** 세 가지만 씁니다(사전 `data/planning_value_status.csv`). 값이 없으면 무엇이 없는지 정확히 적습니다(예: 「미션 목표 수량이 없어요」). 기다린다는 뜻의 옛 상태 낱말은 쓰지 않습니다. 「없음」 한 글자는 원래 보상이 없는 칸(해당 없음)에만 씁니다.
- 아직 원본 표에서 마스터로 옮기지 않은 줄은 `migration_status = 마스터 이전 대기`로 표시합니다.
