# P172 · 엔터파워 · 대표 개발 기획서

**이 문서는** 네 지급처에서 받은 엔터재화를 쌓은 엔터파워(최고 도달 값 · 지금 값 두 값)와, 최고 도달 값으로 여는 아이돌 자리(12문턱) · 팀 칸 · 주사위 배수 · 자동 충전 등 해금, 시즌 투자, 그리고 앉은 스태프 평균으로 보여 주는 기획사 능력의 관계를 설명합니다(11/18 현중 결정 반영 · 옛 4원천 식은 버림).

**보는 법** 1장 · 1-1에서 엔터재화 4지급처와 기획사 능력을 보고 3장의 실행 화면과 4장의 문턱·예외를 확인해 주세요. 규칙 원문은 [전체기획서 04장](../../전체기획서/04_성장건물경제_클로드.html) 「엔터파워」 · 「성장·40자리」입니다. 이전 원문은 짝 로그에 접어 보존합니다.

**지금 상태** 현재 개발되지 않음, 진행 중. 11/18 12:49 발란스(비앙카)가 엔터재화 표(`enter_currency_config.csv` · `enter_currency_grant.csv`)와 해금 표 문턱을 라이브에 적용했습니다. 코드의 엔터파워 계산은 아직 옛 4원천 식(`enter_power_source.csv`)과 스태프 고정 능력치 합(기획사 스탯)으로 동작하며, 엔터재화 식으로 바꾸는 코드는 현재 개발되지 않음, 진행 중입니다. 게임 세션의 캐스팅 문턱 판정은 건물 단계 합 기준으로 동작하며, 현중 11/14 12:34 지시로 지금 상태를 유지합니다. 3~4장의 건물 단계 합 · 눈금 설명은 이 세션 동작입니다.

## 1. 개요

출처: (신규) [P106 건물 성장](건물성장_기획서.html) · [P171 발란스 시뮬레이터](발란스시뮬레이터_기획서.html) · [P110 시즌 경제 참고](../발란스/핵심제안_발란스구조_기획서.html). 이식 비교: 해당 없음.

엔터파워는 잠금 · 상한 해제용 영구 지표이고, **네 지급처에서 받은 엔터재화를 쌓은 값**입니다(현중 11/18 10:06 · 옛 4원천 식(아이돌 수 · 스태프 등급 · 건물 적립 0.65 감쇠 · 팬 단계 합)은 버림). 지급처는 건물 레벨업 45% · 스태프 카드 25% · 아이돌 능력 단계 상승 20% · 팬 카드 10%이고(현중 09:27~09:41), 무료 유저 1년 9,000개 · 하루 12시간 기준입니다(현중 09:48). 엔터재화는 쌓기만 하고 그 값으로 해금을 정하며, 해금은 최고 도달 값으로 읽습니다(현중 12:44). 한 번 오른 엔터파워는 내려가지 않고 계약 해지로도 빠지지 않습니다(현중 09:24). 63일 시즌 끝에 건물 단계가 초기화되어도 엔터파워는 이월됩니다(헌법 제4조). 상세와 라이브 값은 1-1.

```mermaid
flowchart LR
 B["건물 레벨업 45%"] --> EP["엔터파워 = 받은 엔터재화 누계 (최고 도달 값)"]
 T["스태프 카드 첫 입장 25%"] --> EP
 I["아이돌 능력 단계 상승 20%"] --> EP
 F["팬 카드 첫 입장 10%"] --> EP
 EP --> NOW["지금 값 = 최고 도달 값 − 시즌 투자"]
 EP --> C["아이돌 자리 12문턱 (최대 30)"]
 EP --> TS["팀 칸 (최대 10)"]
 EP --> M["주사위 배수 · 충전 상한"]
```

### 콘텐츠 경계

시설 증설의 비용과 효과는 P106, 한 굴림의 경제는 P110과 [P171](발란스시뮬레이터_기획서.html), 실제 멤버 선발은 [P100 오디션](오디션_기획서.html)이 담당합니다. 엔터파워로 생기는 새 멤버 캐스팅권과 다른 기획사와 경쟁하는 [P98 출연권 대전](캐스팅권대전_기획서.html)은 서로 다른 역할입니다.

**기획사 능력**은 엔터재화가 아니라 **지금 앉은 스태프 기준 평균 능력**을 보여 주는 표이고, 이 표가 아이돌 능력을 키우는 공식(앞으로 얻는 양)에 들어갑니다(현중 11/18 13:55 · [05장 R-05-38](../../전체기획서/05_카드캐스팅미니게임_클로드.html)). 팀 등급(루키 · 대세 · 톱티어 · 국민돌 · 글로벌 아이콘)은 스태프 합이 아니라 **팀 아이돌 능력 합**으로 정하고(현중 13:56), 지금 문턱(`idol_team_grade.csv`) 0 · 4,000 · 10,000 · 20,000 · 32,000은 스태프 합(9 × 5★ = 32,400)에 맞춘 값이라 문턱 재산정 필요(비앙카)입니다. 지금 코드는 아직 배치 스태프 고정 능력치 합(`staff_fixed_stat.csv`)을 기획사 스탯으로 셉니다.

## 3. 구동 방법·시뮬레이션

화면 흐름: 시설 단계 확인 → 증설 → 엔터파워 표시 변화 → 배수·충전 상한·캐스팅권 확인. 이식 비교: 해당 없음.

**[발란스 시뮬레이터 열기](/docs/planning/idle-sim.html)** · **[발란스 툴 열기](/docs/planning/balance-tool.html)**

1. 발란스 시뮬레이터에서 건물 단계와 상단 엔터파워 눈금을 함께 확인합니다. 시설을 증설하면 계산에 쓰는 건물 단계가 바뀌고 표시와 배수 조건을 다시 읽습니다.
2. 잠긴 배수의 이유가 엔터파워 문턱인지, 주사위 보유량인지, 그날의 배수 상한인지 구분합니다. 엔터파워가 높아도 해당 실행 경로에 적용되는 나머지 조건이 부족하면 사용할 수 없습니다.
3. 증설로 캐스팅권 문턱을 처음 넘으면 권한을 기록하는 경제 코드가 있습니다. 오디션은 엔터파워에 따른 빈자리 문턱을 별도로 읽으며, 권한 장부를 실제 합류 때 차감하는 전체 연결은 이번 대조에서 확인하지 않았습니다. 문턱 수치는 현재 시험 표를 따릅니다.
4. 일별 기록의 저장된 시설 단계로 당시 값을 다시 볼 수 있습니다. 단계 자료가 없으면 그 기록을 확인 대기로 두고 임의의 시작값으로 채우지 않습니다.

## 4. 상세 기획

### 한 판 순서

엔터파워는 별도 전투 한 판이 아니라 시설 증설 뒤 계산하는 흐름입니다.

| 점검 | 내용 |
| --- | --- |
| 시작·종료 | 증설 조건을 확인하고 단계·눈금과 문턱의 변화를 표시합니다. |
| 입력·출력 | 시설별 전체 단계와 문턱 표를 받아 단계 합·눈금·열림 상태를 계산합니다. |
| 상태와 전이 | 현재 단계 → 증설 성공 시 다음 단계 → 새 눈금입니다. |
| 판정 | 배수·자동 충전 상한·자동 충전 단계와 미지급 캐스팅권 문턱을 각각 확인합니다. |
| 오류·예외 | 최대 단계·돈 부족·비용 미공급은 증설을 막으며, 위치 조건은 도착·자유건설 경로에서 구분합니다. |
| 저장·복원 | 기존 시설 단계와 문턱 지급 기록을 사용합니다. 저장 실패 시 정상 지급으로 처리하지 않습니다. |
| 다른 모듈 연결 | 건물 성장·보드 경제·주사위와 오디션에 연결합니다. |

### 4-1. 시설 단계 합과 눈금

아홉 시설은 사옥·보컬 녹음실·댄스 연습실·콘서트장·뷰티 스튜디오·예능 방송국·프로듀싱 스튜디오·팬샵·아카데미입니다. 현재 계산은 각 시설의 전체 단계를 시설별 최대 단계 이내에서 합합니다. 같은 시설과 연결된 보드 칸이 여러 개이거나 시설의 본관·부속이 여러 동으로 보이더라도 시설 전체 단계는 한 번만 셉니다. 실제 빈 땅의 0은 0으로 유지합니다.

현재 9개 시설을 모두 1단계로 시작하면 합은 9, 모두 30단계면 합은 270입니다. 문턱을 읽는 눈금은 현재 시험식 `반올림(1 + (눈금 최대 − 1) × (단계 합 − 9) ÷ 261)`이고 눈금 최대는 **10,000**입니다(11/17 현중 「엔터파워를 일단 10000으로 올려」 · 전에는 1,000이라 아이돌 자리 문턱 1,050 · 1,200의 9칸이 닿지 않았음). 예를 들어 합 9는 눈금 1, 한 시설을 1단계 올린 합 10은 눈금 39, 합 270은 눈금 10,000입니다. 문턱 표 값은 그대로라 모든 문턱(배수 · 충전 · 몬스 팩 · 자리 · 팀 칸)이 전보다 이른 단계 합에서 열립니다(자리 30칸은 합 41). 문턱 재배분은 비앙카 검토 항목입니다. 합과 눈금은 서로 다른 단위이므로 10단계 합을 눈금 10으로 읽지 않습니다. 건물 수·최대 단계·눈금식의 미래 변경 여부와 운영 문턱은 별도 검토합니다.

```mermaid
flowchart LR
 A[각 시설의 현재 전체 단계] --> B[시설별 최대 범위 확인]
 B --> C[시설마다 한 번씩 합산]
 C --> D[단계 합]
 D --> E[현재 시험식으로 눈금 변환]
 E --> F[표의 문턱과 비교]
```

### 4-2. 배수가 열려도 확인할 조건

현재 배수 문턱 표에는 처음부터 열리는 배수와 엔터파워를 요구하는 배수가 있습니다. 예를 들어 시험 표의 ×10 문턱은 눈금 50이고 ×20 문턱은 100입니다. 실제 적용 조건은 호출 경로를 구분합니다. 공통 `multOptions`는 엔터파워 문턱과 보유량을 검사하고, 일차 상한까지 검사하는 `maxOpenMultOn`은 별도 함수입니다. 현재 허용 범위에서 확인한 수동 경제 연결 함수의 `openMult`·`options`·`roll` 자체는 `multOptions`를 사용하며, 상위 호출의 추가 제한과 전체 화면 동작은 별도 확인 대상입니다. 시험 표는 1일차 최대 ×10, 2일차 최대 ×20을 두고 이후 일차에는 해당 상한 행이 없습니다. 이 수치는 운영 확정이 아닌 현재 시험값입니다.

```mermaid
flowchart LR
 A[배수 선택] --> B{엔터파워 문턱}
 B -- 부족 --> C[필요 눈금 표시]
 B -- 통과 --> D{보유 주사위와 일차 상한}
 D -- 부족 또는 상한 초과 --> E[선택 제한 이유 표시]
 D -- 통과 --> F[해당 배수 사용]
```

자동 충전 상한도 표에서 현재 눈금 이하에 해당하는 마지막 단계를 읽습니다. 하루 자동 충전량은 `enter_power_level`의 auto_charge 단계(눈금 1 → 60 · 100 → 90 · 250 → 120 · 현재 세팅값)에서 같은 방식으로 읽고, 문턱을 넘으면 현황판과 발란스 시뮬레이터가 날아가기와 화살표로 알립니다. 현재 표의 시작 눈금 1에는 같은 문턱의 상한 행이 둘 있으므로 마지막 해당 행을 사용합니다. 표·모델을 읽지 못한 때의 대체 동작은 각 기능에서 다르므로 없어진 값을 실제 0이나 정상 엔터파워로 꾸미지 않습니다.

### 4-3. 새 멤버 캐스팅권

현재 표(`enter_power_level.csv`)는 아이돌 자리를 12문턱에 놓습니다. 증설 전 눈금보다 높고 증설 후 눈금 이하인 문턱을 확인하여, 아직 지급하지 않은 행만 기록합니다. 한 번의 증설에서 여러 문턱을 넘으면 해당 행을 각각 처리합니다. 시작 1칸은 이 12행 밖의 별도 자리입니다(R-05-1).

```mermaid
flowchart LR
 A[증설 전 눈금] --> C[넘은 문턱 찾기]
 B[증설 후 눈금] --> C
 C --> D{이미 지급한 행인가요}
 D -- 아니요 --> E[캐스팅권 지급과 기록]
 D -- 예 --> F[중복 지급하지 않음]
 E --> G[빈 멤버 자리와 오디션 흐름]
```

12문턱은 `100 · 130 · 160 · 190 · 260 · 360 · 480 · 610 · 750 · 900 · 1,050 · 1,200`이고, 문턱마다 `1 · 1 · 1 · 1 · 2 · 2 · 2 · 3 · 3 · 4 · 4 · 5`칸이 열려 시작 1칸과 합쳐 30자리입니다(R-05-2 현재 세팅값). 저장을 제공하는 환경에서 권한 저장이 실패하면 정상 지급으로 처리하지 않습니다.

### 4-3-1. 몬스 팩 자동 지급 · 기획사 등급 보상과 현재 표

기존 몬스 팩 지급 방향의 기록과 현재 원표의 현재 세팅 상태를 구분합니다. 아래 문턱은 현재 표에 있는 값이며 운영 속도·경제·실제 지급이 검수 완료되었다는 뜻은 아닙니다. 이전 헤더와 원문은 짝 로그에 보존합니다.

> **핵심** 엔터파워가 **50 · 100 · 200 · 400 · 700**을 넘을 때마다 **몬스 팩 1개**를 자동으로 줍니다(5번). 캐스팅권과 같은 규칙으로, 문턱을 넘은 줄만 한 번 지급하고 이미 준 줄은 다시 주지 않습니다. 기획사 등급이 **5 · 10 · 15 · 20 · 25 · 30**으로 진화할 때도 한 번씩 줍니다(6번).

```mermaid
flowchart LR
 A[증설] --> B[엔터파워 눈금 오름]
 B --> C{50 · 100 · 200 · 400 · 700 넘음}
 C -- 예 · 처음 --> D[몬스 팩 1 · 보관함]
 C -- 이미 받음 --> E[다시 안 줌]
 D --> F[열기 · 몬스 인벤토리 · 자동 합성]
```

| 문턱 | 지급 | 표(후보 줄) |
|---|---|---|
| 엔터파워 50 · 100 · 200 · 400 · 700 | 몬스 팩 1개씩 · 5번 | `enter_power_level` unlock_kind `mons_pack` · reward_group → `reward_group_entry` card_pack `item_master_card_pack_mons` |
| 기획사 등급 5 · 10 · 15 · 20 · 25 · 30 | 몬스 팩 1개씩 · 6번 | `data/game/agency_grade_reward.csv` → `reward_group` → `reward_group_entry` · 현재 `facility_company` 사옥 단계 1~30 기준 · 별도 기획사명·팀 등급 체계와 구분 |

- 코드: 엔터파워 줄의 reward_group에 카드팩 줄이 있으면 보관함에 넣도록 `config.ts`(줄의 card_pack 읽기) · `session.ts`(문턱 넘을 때 grantPack)에 더했습니다. 현재 원표와 보관함 지급 코드가 있으며, 실제 지급·저장·개봉의 전체 동작은 이번에 실행 검수하지 않았습니다. 열기 · 자동 합성은 [P223 몬스 보유](몬스보유_핵심제안서.html)의 `monsPack.ts`가 맡습니다.
- 시험: [발란스 툴 「몬스 획득 · 합성」](/docs/planning/balance-tool.html?topic=balance_topic_mons_pack)에서 엔터파워 · 기획사 등급 막대를 움직이면 넘은 문턱마다 몬스 팩이 가방으로 날아갑니다.
- 미션(5번) · 유료 샵까지 받는 곳 전체는 P223 4장 「얻기 — 몬스 팩」에 있습니다.

현재 `enter_power_level`의 몬스 팩 행은 `reward_group`과 `reward_group_entry`에 연결되어 있고, 별도 사옥 단계 보상 표도 로더가 읽습니다. `grantPack`은 경제 상태의 팩 보관함과 출처를 쌓는 코드이며 즉시 열거나 합성하지 않습니다. 개봉·자동 합성·미션·상점 전체 연결은 해당 기획과 별도 검수 범위입니다.

### 4-4. 비용 부족·자료 누락과 표시

증설할 시설·최대 단계·비용과 보유 돈을 먼저 확인합니다. 기본 도착 증설은 현재 위치도 검사하지만, [자유건설](P81_설명.html)은 `freeConstruction` 경로에서 위치 조건을 제외하고 같은 단계 비용을 읽습니다. 자유건설이 비용 면제를 뜻하지는 않습니다. 실제 비용 0과 비용이 비어 확인할 수 없는 상태는 다르며, 거래의 단계·잔고·저장 버전 검증과 실패 처리는 별도입니다.

```mermaid
flowchart LR
 A[증설 요청] --> B{시설 위치 단계 비용 확인}
 B -- 불가 --> C[사유 표시와 기존 상태 유지]
 B -- 가능 --> D[비용 차감과 시설 단계 갱신]
 D --> E[눈금과 열린 문턱 갱신]
 E --> F[변화와 알림 표시]
```

발란스 시험 화면은 증설 전후 눈금 차이를 시각 효과로 보여 줄 수 있습니다. 움직임을 줄이거나 화면 연출이 생략돼도 실제 계산값을 다시 읽습니다. 현재 표의 캐스팅권 행은 `reward_group_id`가 비어 있고 몬스 팩 행에는 보상 묶음이 연결되어 있습니다. 몬스 팩 외 추가 혜택은 비앙카 장부 산정 항목입니다. 팬 증가 보정은 원표 `enter_power` 행의 중립 계수를 읽지만, 그 행의 상태는 `비앙카 장부 산정 항목`입니다. 곱해도 값을 바꾸지 않는 현재 중립 입력과 최종 보정값 결정을 구분합니다.
