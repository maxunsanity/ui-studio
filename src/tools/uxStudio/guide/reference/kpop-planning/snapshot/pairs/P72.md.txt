# P72 · 필러 룰렛 · 대표 개발 기획서

> **이 문서는** 보드의 건물 칸에 도착했을 때 판정과 표시용 보상을 보여 주는 필러 룰렛을 설명합니다. 결과는 한 번 정하고 3D 휠에서 보여 준 뒤 현재 건물 단계의 연출로 이어집니다.

> **보는 법** 1장 개요 → 4장 도착 흐름 → 7장 확률 출처 확인 항목 순서로 읽습니다. 실행은 3장의 공용 시뮬레이터 연결에서 확인합니다.

> **지금 상태** 판정·표시 보상·3D 휠·건설 연출 연결 코드가 있습니다. 실제 돈 지급과 칸별 대사·잭팟/전투 연계·효과음은 작업전이며 실제 플레이 검수는 남아 있습니다.

[눌러서 잭팟과 필러 제안서 확인](../../../../proposal-concept/jackpot.html)

## 1. 개요

출처: (합침) 제안서 [잭팟 · 필러 룰렛](../../../../proposal-concept/jackpot.html) · (이식) 모노카피바라 필러 스튜디오 등급 카드 · 책갈피 [P180 도착 판정 계산 모듈](../../../../../../src/simulator/shared/building-arrival.mjs) · [P181 도착 3D 휠 화면](../../../../../../src/ui/board-map/arrival-roulette.mjs) · [P182 도착 판정 설정 표](../../../../../../data/simulator/building-arrival.json)

보드 말이 건물 칸에 멈추면, 그 도착이 얼마나 잘 됐는지를 **올킬 · 차트인 · 광탈** 세 가지 중 하나로 한 번 정하고, 3D 복셀 휠이 그 결과에서 멈추며 결과 이름과 표시 보상을 보여 줍니다. 그 다음 그 칸 건물의 현재 단계 건설 연출로 이어집니다.

### 왜 있는가

- 주사위를 굴려 칸에 도착하는 순간이 매번 같은 숫자로만 끝나면 도착의 긴장감이 없습니다. 모노폴리GO가 칸 도착마다 작은 연출과 보상을 붙이는 것처럼, 우리 보드도 건물 칸 도착마다 「이번 도착은 어땠는지」를 짧은 룰렛 한 번으로 보여 줍니다.
- 결과가 세 단계로 나뉘어 있어야, 같은 칸에 같은 배수로 도착해도 체감이 달라집니다. 올킬은 크게, 차트인은 보통, 광탈은 작게 보이지만 광탈의 판정 계수도 0은 아닙니다(50%, 「완전 꽝 금지」 원칙). 다만 기준값이 0이면 표시 코인은 0입니다.
- 판정은 도착할 때 딱 한 번만 정합니다. 휠은 그 결과를 보여 주는 연출일 뿐 다시 뽑지 않으므로, 화면을 닫거나 다시 열어도 결과가 바뀌지 않습니다.

### 콘텐츠 경계

- 맡는 것: 건물 칸 도착 판정(올킬·차트인·광탈), 판정 확률, 표시 보상 계산식, 도착 3D 휠 화면, 결과 문구, 건설 연출로 넘기는 순서, 칸 도착 필러(독백·조우·사건·등급·리액션·보상 칩·챕터)의 구조와 도착 화면 세 칸(연출·필러·버튼) 배치.
- 다른 문서에 맡기는 것: 건물 단계와 건설·증설 비용([P106 건물 성장](../콘텐츠별_v03/건물성장_기획서.html)), 도착 때 팀 능력이 오르는 성장식(P107 아이돌 성장), 주사위 배수와 이동(P94 공용 시뮬레이터), 잭팟의 확률과 큰 수익([잭팟 제안](../../../../proposal-concept/jackpot.html)), 판정 대사 문장 자체([P63 보드 판정 대사](../../시나리오/보드판정대사_대사초안_v0.html) · [P62 필러 대사](../../시나리오/필러대사_대사초안_v0.html)), 사용 CSV 목록([P92 필러 사용 CSV](../CSV별_v03/filler-csv.html)).

### 현재 기준과 목표

- 대상 칸: 정식 보드 표 `board_tile.csv`에서 `tile_kind`가 `building`인 칸 **24칸**입니다. 8가지 시설이 3칸씩 있고, 출발 칸 사옥(1번)은 건물 칸이 아니므로 대상이 아닙니다.
- 판정 확률의 기획 기준: **올킬 30% · 차트인 30% · 광탈 40%**입니다. 칸 단계·스킬·찬스 카드로 바꾸지 않는 계획을 보존합니다. 현재 표시 전용 설정의 `outcomes[].weight`는 15/50/35이고 policy 라벨은 30/30/40이므로, 아래 「기획·실행 설정·policy 라벨의 세 갈래 출처」와 7장의 확인 항목을 함께 읽습니다.
- 판정 계수: 올킬 **200%** · 차트인 **100%** · 광탈 **50%**입니다.
- 표시 보상: 기준값 × 주사위 배수 × 판정 계수를 계산해 소수점을 버린 코인 수입니다. 이 값은 **표시만** 하고 실제 보유 돈·주사위·카드에 더하지 않습니다.
- 흐름 그림:

```mermaid
flowchart LR
  A[주사위 굴림 · 배수] --> B[말 이동]
  B --> C{도착 칸이 building?}
  C -- 아니오 --> D[그 칸 기능: 찬스·팬 반응·쟁탈전·정산·코너]
  C -- 예 --> E[판정 한 번: 설정 weight]
  E --> F[3D 복셀 휠이 그 결과에서 멈춤]
  F --> G[결과 이름 · ×계수 · 표시 보상 · 성장 요약]
  G --> H[건물 연출 보기: 현재 저장 단계 건설 연출]
  H --> I[메인으로 돌아가기 → 다음 굴림]
```

- 목표: 도착 한 번에 판정 한 번, 결과는 바뀌지 않고, 화면은 짧게, 이어서 건물 연출. 실제 돈: 건물 칸 25칸(출발 1 사옥 포함) 모두 도착 돈 × 판정 배율(올킬 2 · 차트인 1 · 광탈 0.5) × 주사위 배수, 칸 차등 기타 0.470 < 방송국 0.988 < 콘서트홀 1.034(총량 유지 · 임시(나중에 결정)).

## 3. 구동 방법·시뮬레이션

화면 흐름: [보드 주사위 굴림 · 이동] → [이 화면: 도착 필러 룰렛] → [건물 연출 보기 · 메인으로 돌아가기] · 스샷 미완 · 이식 비교 [모노카피바라 필러 스튜디오 등급 카드]

[눌러서 도착 필러 시뮬레이터 실행](../../../../game-simulator.html?module=simulator_module_filler) · [눌러서 건설 모듈의 도착 테스트 실행](../../../../game-simulator.html?module=simulator_module_building)

건물 칸 직접 테스트는 「건설」 모듈의 도착 요청·검사 미리보기 경로에서 합니다. 모바일 공용 화면에서 도착 요청이나 검사 조건 없이 여는 기본 건설 화면은 자유건설로 갈 수 있으므로, 아래의 칸 선택 테스트와 구분합니다. 문서를 열 때 시뮬레이터나 3D 화면을 자동 실행하지 않습니다.

### 시뮬레이터 모듈

| 모듈 ID | 화면 이름 | 진입 파일 | 문서 | 하는 일 |
|---|---|---|---|---|
| simulator_module_filler | 도착 · 필러 | `docs/planning/_runtime/simulator/idol_growth.js` (소스 `src/simulator/idol_growth.mjs`) | P72 | 주사위·이동·도착을 돌려 건물 칸 도착을 만듦 |
| simulator_module_building | 건설 | `docs/planning/_runtime/simulator/defense.js` (소스 `src/simulator/defense.mjs`) | P106 | 3D 도시에서 건물을 고르고 건설·증설. 건물 도착이 오면 도착 필러 룰렛을 띄움 |

- 공용 호스트에는 모듈·도시를 재사용하고 화면 전환 때 중단·가시성을 알리는 경로가 있습니다. 다만 「도착 · 필러」는 별도 iframe 연결이고 「건설」은 호스트의 도시를 받으므로, 두 경로의 도시 공유·문서 왕복 복구는 상위 연결과 실제 구동을 따로 확인해야 합니다.

### 도착 요청부터 복귀까지

```mermaid
flowchart LR
 A[메인에서 건물 칸 도착] --> B[칸 번호와 배수 전달]
 B --> C[한 번 판정한 영수증]
 C --> D[휠 회전과 결과 공개]
 D --> E[현재 단계 건물 연출]
 E --> F[메인으로 돌아가기]
 C --> G[같은 결과 다시 보기]
 G --> D
```

### 메인에서 도착이 들어올 때

1. 공용 시뮬레이터에서 주사위를 굴립니다. 굴린 주사위 배수(×1 이상)가 도착 요청에 함께 실립니다.
2. 말이 building 칸에 멈추면 메인이 도착 요청(칸 번호 `boardIndex`, 배수 `multiplier`, 요청 ID `requestId`)을 만듭니다.
3. 건설 모듈이 도착 요청을 받으면 그 칸의 시설을 고르고, `resolve()`로 판정을 **한 번** 만듭니다. 요청 ID가 판정 씨앗(seed)입니다. 이미 만든 판정이 함께 넘어오면(`environment.buildingArrival`) 새로 뽑지 않고 `accept()`로 그대로 받습니다.
4. 화면이 켜지는 것은 휠이나 사람의 확인을 기다리지 않습니다. 휠은 따로 돌기 시작합니다.
5. 휠이 결과 칸에서 멈추면 결과 이름·계수·표시 보상·성장 요약이 나타나고 「건물 연출 보기」 버튼이 보입니다.
6. 「건물 연출 보기」를 누르면 그 칸 건물의 **현재 저장 단계** 건설 연출을 봅니다. 건물 단계는 바꾸지 않습니다. 0단계면 빈땅 그대로입니다.
7. 「메인으로 돌아가기」(또는 상단 메인 이동)를 누르면 같은 건물 도착 기록을 닫고 다음 굴림을 허용합니다. 중간에 나가면 취소(`cancelled`)로 한 번 기록하고 대기 중인 도착을 풉니다.

### 건물 칸을 골라 직접 테스트할 때

1. 건설 모듈에서 24칸 중 한 칸을 고릅니다. 화면 제목은 「24개 대지 도착 테스트」, 안내는 「오디션 없이 선택한 칸의 필러·보상·건물 연출을 확인합니다.」입니다.
2. 「선택한 칸 도착 테스트」를 누르면 메인 도착과 같은 `resolve()` 경로에서 설정의 `outcomes[].weight`로 판정하고 같은 화면을 보여 줍니다. 기획 기준 30/30/40과 현재 설정의 차이는 4장 출처 대조에서 구분합니다.
3. 「같은 결과 다시 보기」는 같은 판정을 다시 재생합니다. 새로 뽑지 않습니다.

### 저장·복원·중단

- 판정 결과(영수증)는 도착 기록에 한 번 남습니다. 같은 도착으로 돌아오거나 다시 보여 줄 때는 `accept()`가 영수증을 검사해 그대로 씁니다. 재추첨·재지급은 없습니다. 이는 모듈의 영수증 수용·직렬화와 허브 반환 경로 설명이며, 상위에서의 보관·새로고침 복원과 실제 저장 검수는 별도입니다.
- 휠이 도는 중에 메인으로 돌아가면 「룰렛을 확인하는 중이에요. 메인으로 돌아가면 연출을 건너뜁니다.」 안내 뒤 연출을 건너뜁니다.
- 실제 계정 저장, 서버 저장은 작업전입니다.

## 4. 상세 기획

### 한 판 순서 (확정 · 코드 `building-arrival.mjs` · `arrival-roulette.mjs` · `defense.mjs`)

| 점검 | 내용 |
|---|---|
| 시작·종료 | 시작: 메인 도착 요청이 building 칸으로 들어오거나, 건설 모듈에서 「선택한 칸 도착 테스트」를 누름. 종료: 「건물 연출 보기」 뒤 연출이 끝나거나 「메인으로 돌아가기」를 누름 |
| 입력·출력 | 입력: 칸 번호(`boardIndex`), 주사위 배수(`multiplier`, 1 이상), 씨앗(`seed` = 요청 ID), 성장 요약(`growthTotal`, 없으면 비움). 출력: 영수증(아래 「영수증 필드」) |
| 상태와 전이 | 대기 → 도는 중(휠 회전, 결과·금액 숨김) → 결과 공개(이름·계수·표시 보상·성장 요약, 「건물 연출 보기」 보임) → 건물 연출 → 닫힘. 어느 단계에서든 취소 시 닫힘(`cancelled`) |

| 오류·예외 | 설정 버전이 1이 아니거나 `presentationOnly`가 true가 아니면 「도착 필러 설정을 확인해 주세요.」 · building 칸 수가 24가 아니거나 칸 ID가 겹치면 「정식 24개 대지 연결을 확인해 주세요.」 · 결과가 3개가 아니거나 이름이 겹치거나 확률 합이 100이 아니면 「도착 룰렛 확률 합을 확인해 주세요.」 · 값이 비었거나 숫자가 아니거나 음수면 「도착 룰렛 ○○ 값을 확인해 주세요.」 · 칸이 building이 아니거나 씨앗이 없거나 배수가 1 미만이면 「건물 도착 정보를 확인해 주세요.」 |

### 기획·실행 설정·policy 라벨의 세 갈래 출처

| 역할 | 기록된 내용 | 읽는 방법과 확인 경계 |
|---|---|---|
| 이 문서의 기획 기준 | 올킬 30% · 차트인 30% · 광탈 40% | 기존 계획으로 보존합니다. 현재 설정과 차이가 있어 실제 실행값·최종 결정으로 단정하지 않습니다. |
| 표시 전용 실행 설정 | `building-arrival.json`의 `outcomes[].weight` = 15/50/35, `presentationOnly=true` | `loadBuildingArrival()`은 이 weight를 읽고 `resolve()`가 판정에 사용합니다. 표시 영수증이며 실제 지갑 지급 확률을 뜻하지 않습니다. |
| 같은 설정의 policy 라벨 | `probabilityPolicy=fixed_user_20261021_30_30_40` | 정책 이름 문자열입니다. 로더가 문자열의 숫자를 해석하거나 weight 대신 쓰지 않습니다. |

기획 기준과 실행 설정·라벨은 역할을 구분해 함께 보존합니다. 어느 값이 의도된 최종 기준인지 직접 결정 근거는 아직 대조하지 못했습니다. 표시 전용 설정의 차이를 실제 운영 지급 확률의 오류로 확대하거나, 숫자가 같은 보드 경제 설정과 자동으로 합치지 않습니다.

### 판정 확률과 계수 (기획 기준과 실행 설정 대조 · `building-arrival.json` `outcomes` · `economy_config.csv`)

| 판정 키 | 화면 이름 | 아이콘 | 색 | 기획 기준 (30/30/40) | 계수 열 (`economy_config`) | 계수 |
|---|---|---|---|---|---|---|
| great (economyKey big) | 올킬 | ✦ | #efbf51 (금색) | 30 | hit_big_factor_pct | 200% (×2) |
| mid | 차트인 | ♪ | #b7a1ec (보라) | 30 | hit_mid_factor_pct | 100% (×1) |
| miss | 광탈 | ☁ | #8dc7dc (하늘) | 40 | hit_miss_factor_pct | 50% (×0.5) |

- `probabilityPolicy` 라벨은 `fixed_user_20261021_30_30_40`입니다. 로더는 이 문자열을 확률 수치로 해석하지 않고 `outcomes[].weight`를 읽습니다. 세 weight의 합이 100이 아니면 화면이 열리지 않고 오류를 냅니다. 기획 기준·현재 설정·라벨의 정합과 직접 결정 근거는 7장의 확인 항목입니다.
- `economy_config.csv`에는 `hit_big_weight` 15 · `hit_mid_weight` 50 · `hit_miss_weight` 35 줄도 남아 있습니다. 이 세 줄은 필러 룰렛이 읽지 않습니다. 필러 룰렛은 같은 표에서 **계수 세 줄만** 읽습니다.
- 확률 보정: 없음. 건물 단계, 스킬, 찬스 카드, 연속 광탈 보상 같은 보정은 넣지 않습니다.
- 기획 기준 30/30/40의 계산 예: 0.30×2 + 0.30×1 + 0.40×0.5 = 1.10. 기획상 평균 표시 보상은 기준값×배수×1.1입니다(위 기획 표만으로 계산한 값). 현재 JSON 설정의 기대값으로 읽지 않습니다.

```mermaid
flowchart TD
 A[보드 칸과 기본 수익] --> D[표시 코인 계산]
 B[이번 굴림의 배수] --> D
 C[판정별 계수] --> D
 D --> E[내림한 표시 코인]
 E --> F[화면에만 표시]
 F --> G[실제 지갑은 변경하지 않음]
```

### 표시 보상 계산 (확정 · `building-arrival.mjs` `resolve`)

계산식: **표시 코인 = 내림(기준값 × 주사위 배수 × 판정 계수)**

- 기준값: 그 칸 `board_tile.base_income` 칸이 비어 있지 않으면 그 값을 쓰고, 출처 문구 「보드 기본 수익 사용」을 보여 줍니다. 비어 있으면 설정의 임시 기준값 `temporaryBaseMoney` **1000**을 쓰고 「기본 수익 미정 · 임시값 사용」을 보여 줍니다.
- 주사위 배수: 메인에서 굴린 배수. 1보다 작으면 오류입니다. 직접 테스트에서는 1입니다.
- 판정 계수: 위 표의 2 · 1 · 0.5.
- 결과가 안전한 정수가 아니면 오류로 멈춥니다.

계산 예(임시 기준값 1000일 때):

| 경우 | 배수 | 판정 | 계산 | 표시 코인 |
|---|---|---|---|---|
| 1 | ×1 | 올킬 | 1000 × 1 × 2 | 2,000 |
| 2 | ×1 | 차트인 | 1000 × 1 × 1 | 1,000 |
| 3 | ×1 | 광탈 | 1000 × 1 × 0.5 | 500 |
| 4 | ×2 | 올킬 | 1000 × 2 × 2 | 4,000 |
| 5 | ×2 | 차트인 | 1000 × 2 × 1 | 2,000 |
| 6 | ×2 | 광탈 | 1000 × 2 × 0.5 | 1,000 |

- 지금 표의 실제 값: 24칸 모두 `base_income`이 `0`으로 들어 있습니다. 코드는 「빈칸」만 임시값으로 바꾸므로, 지금 시뮬레이터에서는 기준값 0 → 표시 코인 **0**, 출처 「보드 기본 수익 사용」이 나옵니다. 칸 수익 값은 발란스 대기입니다(남은 결정 참고).
- 표시 보상은 `displayedReward`에 코인만 담고 주사위 0, 카드 0입니다. 화면 아래에 「임시 표시 보상입니다. 실제 보유량에 더하지 않습니다.」가 항상 붙습니다.
- 실제 돈 지급은 작업전입니다. 칸 수익은 그 칸 건물 단계를 따라 오르도록(모노폴리GO 보드 단계 역할) 설계되어 있고, 숫자는 발란스 대기입니다.

### 도착 성장 요약 (확정 · 기존 성장식 사용)

- 도착 때 팀 능력이 오르는 양은 P107의 기존 도착 성장식이 계산합니다. 필러 룰렛은 그 결과 숫자(`growthTotal`)만 받아 「이번 도착 팀 능력 +○」로 보여 줍니다.
- 성장 숫자가 없으면 「도착 성장 수치는 기존 성장 계산을 사용합니다.」를 보여 줍니다. 현재 건설 모듈의 기본 판정 호출은 성장 요약을 넘기지 않으며, 전달된 영수증에 `growthTotal`이 있을 때만 숫자를 표시합니다. 상위에서 이 값을 공급하는 연결은 미확인입니다.
- 룰렛은 성장을 다시 뽑거나, 다시 계산하거나, 판정 계수를 성장에 곱하지 않습니다. 같은 판정을 기존 판정 칸에 한 번 넘기는 것까지가 이 문서의 몫입니다.
- 도착만으로 건물 단계를 1 올리지 않습니다.

### 도착 화면 세 칸 (확정 · `arrival-roulette.mjs` 나눔 배치)

칸에 도착하면 화면을 세 칸으로 나눕니다. 기준은 모노카피바라입니다(무대, 필러 창 `filler-pane`, 아래 버튼 줄 `dock`의 `cta-row`가 따로).

| 칸 | 하는 일 | 넣는 것 | 넣지 않는 것 |
| --- | --- | --- | --- |
| 연출 | 도착을 보여 주기 | 3D 복셀 휠(나눔 배치에서는 휠만 화면 가득) | 버튼, 금액 |
| 필러 | 그 칸의 이야기와 결과 | 「{번호}번 · {이름}」, 제목 「도착 필러 룰렛」, 도는 중 안내, 확률 범례(`data.outcomes`의 이름·weight; 기획안은 올킬 30% · 차트인 30% · 광탈 40%), 결과 「{이름} · ×{계수}」, 「표시 보상 · {코인} 코인」, 성장 요약, 기준값 출처, 표시 전용 안내 | 누르는 버튼 |
| 버튼 | 손이 고르는 것 | 「건물 연출 보기」, 「메인으로 돌아가기」 | 대사, 휠 |

- 시뮬레이터가 필러 칸과 버튼 칸 자리를 주면 위처럼 나눠 그립니다. 자리를 주지 않으면 한 장짜리 카드(가로 최대 420px, 휠 310×250px) 안에 위 순서대로 모두 넣습니다.
- 「건물 연출 보기」는 휠이 멈추고 결과가 공개된 뒤에만 보입니다. 도는 동안에는 결과 이름·금액·성장 요약·출처가 비어 있습니다.
- 「메인으로 돌아가기」는 처음부터 보입니다.

### 올킬 뒤 2차 스케줄 룰렛 (확정 · 코드 `src/game/economy/session.ts` · `src/simulator/shared/hub-client.mjs` · 표 `second_roulette_reward.csv`)

보드 경제(돈을 실제로 계산하는 쪽)는 건물 칸 도착 돈을 계산할 때 판정이 **올킬(big)일 때만** 보상 꾸러미에 `show = schedule_roulette`를 붙입니다. 차트인·광탈이면 `show`가 비어 있어 연출 없이 바로 받습니다. 올킬은 최초 표시 후보이며, 뒤에서 별도 2차 룰렛 노출 확률로 다시 걸러질 수 있습니다. 이동은 최종 보상 꾸러미의 `show`를 기준으로 하므로 올킬마다 항상 2차 룰렛이 열리는 것은 아닙니다.

- 판정이 붙는 조건: 그 칸 보상 기준표 줄에 판정 사용(`moneyJudge60`)이 켜져 있고, 그 칸 건물 단계가 1 이상일 때. 건물 단계가 0이면 돈 0, 판정 없음.
- 보드 경제의 판정 확률: `economy_config`의 `hit_big_weight` 15 · `hit_mid_weight` 50 · `hit_miss_weight` 35를 읽습니다. 계수는 같은 표의 200/100/50%입니다. 표시 전용 필러는 별도로 `building-arrival.json#outcomes`를 읽습니다. 현재 숫자가 같더라도 같은 지급 경로나 정책 확정을 뜻하지 않으며, 기획 기준·실행 설정·policy 라벨은 출처 대조에서 구분합니다.
- 건물 칸 도착 돈 = 내림(S 대비 단계별 % × 판정 계수 × 주사위 배수 × 이벤트 돈 버프) + 그 건물 팬 보너스.
- 화면 길: 보상 꾸러미에 `show = schedule_roulette`가 있고 칸이 찬스·팬 반응 칸이 아니면, 허브가 건물 화면보다 먼저 이벤트 룰렛 `wheel_schedule`(스케줄 룰렛, 바늘형 8칸)로 보냅니다. 찬스 칸 8·23·38은 콘서트 룰렛으로 갑니다. 팬 반응 칸 3·18·34는 룰렛 없이 받습니다.
- 2차 룰렛 칸(`second_roulette_reward.csv`, `minigame_id = schedule_roulette`, 각 weight 1): 돈 행의 받는 양·등급 추가량은 S 대비 퍼센트를 돈으로 환산하는 입력이고, 주사위·카드·덱 행은 개수·장수 입력입니다. 아래 값 자체를 현재 운영 승인값으로 정하는 설명은 아닙니다.

### 게임 화면 구조에서의 자리 (확정 · `simulator-system-flow.json` · 툴 [P190 게임 화면 구조](../../../../flow-page.html?page=arrival))

### 확률 출처 확인 항목

- 표시 전용 경계: `presentationOnly=true`와 표시 영수증을 유지하며, 실제 지갑·건물 단계 지급 정책과 구분합니다.
- 실제 읽기: 로더가 `outcomes[].weight`를 읽고 합 100을 검사하며, UI 범례도 `data.outcomes`의 이름·weight를 사용하는지 확인합니다. 현재 소스 대조값은 15/50/35입니다.
- 직접 결정 미확인: 기획 기준 30/30/40, 실행 설정 15/50/35, policy 라벨 30/30/40의 차이가 의도된 것인지 최신 직접 결정 원문과 대조해야 합니다. 새 확률 확정이나 코드·표 수정은 이 문서 정리에서 하지 않습니다.
- 실제 화면 미검수: 이번에는 원문·설정·로더·UI 코드를 대조했습니다. 책갈피 진입·독서·하단 접기와 실행 화면의 실제 표시는 별도 검수입니다.

### 수락 기준

- building 24칸에 도착할 때만 룰렛이 열리고, 나머지 16칸은 그 칸 기능으로 갑니다.
- 한 도착에 판정은 한 번이며, 다시 보기·복귀·새로고침으로 결과가 바뀌지 않습니다.
- 표시 전용 판정은 설정의 `outcomes[].weight`를 읽고, 합이 100이 아니면 화면을 열지 않습니다. 기획 기준 30/30/40과 policy 라벨의 정합·직접 결정 근거는 7장의 확인 항목으로 남깁니다.
- 표시 코인은 내림(기준값 × 배수 × 계수)이며 실제 보유량에 더하지 않습니다.
- 휠이 멈추기 전에는 결과 이름·금액을 보여 주지 않습니다.
- 「건물 연출 보기」는 현재 저장 단계만 보여 주고 건물 단계를 올리지 않습니다.
- 표 값이 비었거나 틀리면 오류를 보여 주고 임의 값을 만들지 않습니다.
