# P148 · 테이블 데이터 조합 구조 · 시스템 개발 기획서

**이 문서는** 모든 시스템을 **마스터 표 + 이어진 종류 · 옵션 · 효과 표**로 만드는 기획 방향과, 현재 다섯 종류의 표가 실제 코드에서 쓰이는 범위를 나누어 설명해요. 새 기능을 표로 확장하는 방향을 유지하되, 표가 있다는 이유만으로 모든 연결이 끝났다고 보지 않아요.

**보는 법** 1장(원칙) → 2장(구조도) → 3장(현재 사용 범위) → 4장(남은 연결과 검증)을 읽으세요. 첫 표 기획은 [P58](../../기획서/기획서_테이블데이터기초_v0.1_이스라트.md), 전환 방향의 근거는 [P150 · 10/17 현중 결정 원문](../../../입력/검토-테이블구조_현중결정_1017.md)이에요. P150은 당시 결정 원문을 그대로 보존하는 예외 문서이며, 현재 코드 설명을 새 결정으로 덧붙이지 않아요. 지난 전문은 [로그](테이블데이터_조합구조_기획서.log.md)에 있어요.

**지금 상태** **개발된 부분**: 마스터와 하위 표, 경제의 일부 하위 표 소비, 캐릭터·스킬 마스터 ID를 읽는 편성·시연 코드가 있어요. **현재 개발되지 않음·진행 중인 부분**: 모든 소비자의 전환, 스킬 연결·옵션의 실행 연결과 전체 관계 선언·검증, 미연결 화면과 배포 결과 확인이에요. `마스터 이전 대기`는 이전 상태를 적은 칸이며, 그 표가 모든 코드에서 쓰이지 않는다는 뜻은 아니에요. 이번 문서 보완은 실제 게임 작동·저장·화면 검수를 새로 완료한 기록이 아니에요.

## 1. 원칙

1. 발란스 값은 모두 CSV에서 바꾸는 방향이에요. 빈 값은 `발란스 대기`로 남겨요.
2. 데이터 종류마다 마스터 하나를 두고, 종류 전용 칸은 마스터 ID를 쓰는 하위 표로 나누어요. 콘텐츠마다 같은 대상을 새로 정의하지 않아요.
3. ID는 표 이름 전체를 쓴 풀네임과 고정 원칙을 따르며, **하위 표가 마스터 ID를 같이 쓰는 예외**는 P150의 기존 결정이에요. 현재 원표에는 기존 키 형식과 원본 참조가 함께 남아 있어요. 이 문서 보완에서 ID를 바꾸거나 새로운 전환 승인을 만들지 않아요.
4. 종류 값은 `enum_value`에 등록된 것을 써요. 종류 등록과 실제 행의 종류 사용은 따로 확인해요.
5. 시뮬·게임·발란스툴이 같은 원표와 계산을 읽는 방향이에요. 실제 읽는 표·계산·저장 주체는 [S17의 현재 도구 경계](../../시스템기획/S17_기획서툴_제작기본양식_v02.md#current-tool-boundaries)처럼 실행 경로마다 확인해요.

<a id="structure"></a>
## 2. 구조도

```mermaid
erDiagram
  enum_value ||--o{ item_master : "item_type"
  item_master ||--o{ reward_group_entry : "reward_ref_id"
  currency_master ||--o{ reward_group_entry : "reward_ref_id"
  reward_group ||--|{ reward_group_entry : has
  skill_master ||--o{ skill_link : links
  skill_link }o--|| missile : "link_type=missile"
  skill_link }o--|| aura : "link_type=aura"
  ability_master ||--|{ ability_detail : "세부"
  building_master ||--o{ facility_growth_level : "단계"
```

위 그림은 기존 **기획 관계도**예요. 위쪽은 경제(아이템·재화 → 보상 묶음), 가운데는 전투(스킬 → 미사일·오라), 아래는 성장(능력·건물)을 보여 주어요. 보상을 보상 묶음 ID로 가리키는 방향과 표별 선언·실제 사용 여부는 구분해요. 그림의 모든 연결이 현재 스키마의 FK로 선언되어 있거나 모든 실행 경로에서 소비된다는 뜻은 아니에요.

| 그림과 실제 표의 관계 | 현재 구분 |
|---|---|
| 스킬 → `skill_link` → `missile`·`aura` | 연결·옵션 표는 있어요. `skill_link`·`missile_option`·`aura_option`을 직접 읽는 실행 소비자는 이번에 확인한 소스 범위에서는 확인하지 못했어요. 전역 미구현 판정은 아니에요. |
| 건물 → `facility_growth_level` | 기존 성장 원표도 남아 있어요. 공통 경제는 `building_master_level`을 읽고, core-proposal의 기본 레슨 배수도 이 합친 표를 읽어요. 비용·팬·능력·기본수익은 여전히 `facility_growth_level`을 읽는 경로가 있어요. |
| 맵·보드 | `map_master`·`board_master`라는 새 마스터를 임의로 만들지 않아요. 현재 `board_tile`·`map_node`·`map_path`, 그림 배치용 `map.json`의 역할을 아래에서 구분해요. |

## 3. 현재 사용 범위

### 3-1. 다섯 종류의 등록과 실제 소비

| 종류와 현재 원표·구조 | 이번에 확인한 코드 사용 | 아직 같은 뜻으로 볼 수 없는 것 |
|---|---|---|
| **아이템** · `item_master`와 `item_master_dice_mult`·`item_master_shop_gem_ladder`·`item_master_shop_sku`·`item_master_card_pack`·`item_master_sale_offer`·`item_master_casting` 하위 표가 있어요. 일부 하위 표는 파일·열 선언이 있어도 schema의 상태는 `unregistered`예요. | 경제 배수 이름은 마스터, 배수 값은 하위 표에서 읽어요. 공통 상점은 상품·보석 하위 표와 비용·보상 묶음을 읽어요. 카드북·특가에도 각 하위 표 소비 경로가 있어요. | 마스터 부모 행 추가만으로 상품 가격·보상·운영 결제가 생기는 것은 아니에요. 모든 소비자의 마스터 전환이나 운영 완료도 뜻하지 않아요. |
| **캐릭터** · `character_master`의 종류·원본 참조가 있고, 행의 이전 상태는 `마스터 이전 대기`예요. | 캐스팅 대결의 편성 로더는 캐릭터 마스터 ID를 조회하고 `mons` 종류·원본 ID를 확인해요. 캐스팅 진입에도 마스터를 읽는 경로가 있어요. | 이전 대기 행을 전부 미사용으로 보지 않아요. 기존 원본 참조를 쓰는 코드까지 모두 새 ID로 전환했다는 뜻도 아니에요. |
| **스킬** · `skill_master`와 `skill_link`·미사일·오라·옵션 표가 있어요. | 캐스팅 대결은 스킬 마스터를 조회한 뒤 디펜스 스킬의 원본 ID를 화면 설정에 연결해요. 나쁜 기운 쪽은 기존 스킬 원표를 읽는 경로도 남아 있어요. | 일부 마스터 사용을 스킬 연결 그래프·옵션 전체 구현으로 확대하지 않아요. 연결 표의 FK 선언과 실제 옵션 적용은 별도 확인 대상이에요. |
| **맵·보드** · `board_tile`·`map_node`·`map_path`가 등록되어 있어요. `map.json`은 그림 배치 자료예요. | 보드 로더는 칸 표와 노드·연결을 읽고, 보드맵은 칸의 시설·종류를 칸 표에서 붙여요. 건물 이름은 마스터를 읽는 경로가 있어요. | 별도 `map_master`·`board_master`의 등록·구현 완료로 부르지 않아요. 실제 기준 자료와 하위 관계가 이미 있는 것부터 구분해요. |
| **건물** · `building_master`, 건물 축·단계 하위 표와 합친 `building_master_level`이 있어요. 옛 시설 행과 이전 대상 참조도 남아 있어요. | 공통 경제 로더는 건물 마스터·합친 단계 표 등을 읽어요. core-proposal의 기본 레슨 배수는 합친 표, `legacy` 비교는 기존 성장 표를 읽어요. | 합친 표 사용을 모든 열·화면·옛 시설의 전환 완료로 보지 않아요. 그림 배치·단계·기존 성장 원표의 역할을 함께 남겨요. |

### 3-2. 오디션 몬스의 이전 계획과 현재 분류

P150의 「오디션 mons를 별도 종류로 남김」은 **10/17 결정 원문**으로 보존해요. 현재 `character_master`의 오디션 풀 참조 행은 `character_type=mons`이고, `enum_value`에는 별도 `audition_mons` 종류 선언도 남아 있어요. 이 차이는 원문 결정과 현재 데이터 분류의 확인 항목이며, 이번 문서에서 합침 승인이나 새 종류를 결정하지 않아요.

오디션 풀 참조가 있다고 오디션의 새 몬스 지급을 뜻하지는 않아요. [현재 P100 오디션 기획](오디션_기획서.md)은 합류 때 몬스를 지급하지 않으며, 기존 풀은 색·자산과 옛 저장의 짝 정보 호환 자료로 설명해요. 획득 정책과 마스터 분류·원본 포인터를 섞지 않아요.

### 3-3. 기존 개발 기록과 현재 확인 범위

기존 문서에는 미션·카드북 수집 보상·특가·이벤트·모험의 경제 전환, `economy_live_config`, `resource_master`·`resource_variant`·`resource_link`와 `src/data/resourceMaster.mjs`, `event_module_registry`의 모듈 등록을 개발 기록으로 적어 두었어요. **기존 결과 동일 확인 기록은 하단 이전 기록과 로그에 보존**하며, 이번 다섯 종류 대조에서 그 모든 기능의 실행·저장을 다시 시험한 것으로 표시하지 않아요.

기존 상점 SKU에 맞춘 마스터 부모 이름·종류·원본 참조 추가는 정체성 연결 보완이에요. 가격·보상·하위 SKU·스키마 변경과 구분하며, 선택한 관계 검사 결과도 아래 범위만 뜻해요.

### 3-4. 기존 표 목록 입구

아래는 실제 `planning_csv_table`에 등록된 key를 사용한 **목록 입구**예요. 목록을 읽고 참조 항목으로 이동하는 검수와, 전체 데이터 관계·게임 작동을 확인하는 검수는 구분해요.

| 종류 | 기존 등록 주소 |
|---|---|
| 아이템 | [item_master](/docs/planning/game-table-tool.html#item_master) |
| 캐릭터 | [character_master](/docs/planning/game-table-tool.html#character_master) |
| 스킬 | [skill_master](/docs/planning/game-table-tool.html#skill_master) |
| 맵·보드 | [board_tile](/docs/planning/game-table-tool.html#board_tile) · [map_node](/docs/planning/game-table-tool.html#map_node) · [map_path](/docs/planning/game-table-tool.html#map_path) |
| 건물 | [building_master](/docs/planning/game-table-tool.html#building_master) |

`item_master_shop_sku`·`building_master_level` 등 이번 목록에서 정확한 key 등록이 확인되지 않은 실제 표에는 목록 주소를 새로 만들어 붙이지 않아요.

<a id="remaining"></a>
## 4. 남은 연결과 검증

| 구분 | 현재 뜻과 남은 확인 |
|---|---|
| 등록과 파일 | schema 등록 상태, 실존 CSV와 열 선언, 표 목록 입구는 서로 달라요. 파일이 있다고 등록·화면 연결 완료로 보지 않아요. |
| 이전 상태 | `migration_status`는 이전 상태예요. `마스터 이전 대기`를 전부 미구현으로, 빈칸·신규를 운영 승인으로 바꾸지 않아요. |
| 연결·옵션 | `skill_link`·옵션 등 직접 실행 연결이 확인되지 않은 범위는 연결 대기로 남겨요. 실제 소비자와 선언 근거를 더 확인해야 해요. |
| PK·FK | 표마다 기본 키·외래 키 선언 범위가 달라요. 공통 로더는 선언된 FK와 같은 호출에 함께 읽은 대상만 검사하고, 기본 보고는 경고예요. 캐스팅 편성의 고유 키·ID 조회 검사는 별도 코드에 있어요. |
| 선택 관계 검사 | 부모 정체성 보완 뒤 선택한 14개 비어 있지 않은 ID 관계의 누락 0이 보고되었어요. 빈칸의 정책, 모든 PK·FK 선언, 전체 표 의미·운영 결과를 검사한 수치는 아니에요. |
| 생성 검사 | 본체가 수행한 schema 생성물 `--check` 통과는 원본과 생성물 일치 확인이에요. 전체 FK·모든 소비자 전환·실제 화면·운영 저장 완료를 뜻하지 않아요. |
| 화면·빌드 | 실제 화면, 배포 결과와 남은 옛 표 소비자는 각 경로별 검수 대상이에요. 기존 문서의 옛 빌드 이름 집계는 이전 기록으로 보존하고, 이번 새 집계나 빌드 완료로 쓰지 않아요. |
| 문구·check_list | 문구 마스터, 출처 문서 등록과 `check_list`·`tables` 값 정리는 기존 남은 항목이에요. 이번에는 새 표나 값을 만들지 않아요. |
