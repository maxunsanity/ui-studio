# P102 · 게릴라 공연 · 대표 개발 기획서

**이 문서는** 상대의 공연장에 게릴라 무대 트럭이 나타나고, 관객석을 하나씩 열어 같은 종류의 팬을 먼저 모으는 공연을 설명합니다. 돈과 팬, 카드 또는 기분 간식이 어떻게 연결될지를 살펴보는 기획입니다.

**보는 법** 1장 개요 → 3장 구동 방법·시뮬레이션 → 4장 상세 기획 → 6장 표·7장 검수 순서로 읽습니다. 기존 제안 링크와 출연권 대전 시뮬레이터는 별도 참고로 구분합니다.

**지금 상태** 현재 개발되지 않음, 진행 중(이 문서의 게릴라 공연 진입·정산 연결 기준). 실제 게릴라 공연 구동·정산·저장은 미검수이며, 수치·확률·보호선은 발란스 대기입니다.

[눌러서 게릴라 공연 제안 확인](../../../../proposal-fansim-casting.html)

## 1. 개요

트럭이 멈추고 해치가 열리면 팬들이 관객석으로 몰려옵니다. 플레이어는 자리를 열며 어떤 팬이 나왔는지 확인하고, 같은 종류가 세 명 모이면 공연 결과와 보상을 봅니다. 두 명이 모였을 때 다음 자리가 반짝이는 연출과 숨은 응원봉 배수 자리는 기대감을 높이는 장치입니다.

이 문서의 트럭·좌석·서버 선결정·팬 이동은 **구현을 위한 기획**입니다. 현재 쟁탈 시뮬레이터는 출연권 대전으로 진행하며 게릴라 공연의 실제 진입·정산은 연결되지 않았습니다. 팬 이동과 돈 지급도 게임에서 이미 일어나는 일로 읽지 않습니다.

```mermaid
flowchart LR
 A[쟁탈 도착에서 진입 경로 결정] --> B[공연 트럭 도착과 해치 열림]
 B --> C[관객석 선택과 팬 공개]
 C --> D[같은 종류 세 명 모임]
 D --> E[보상과 팬 이동 결과 확인]
 E --> F[보드 복귀와 상대 알림]
```

## 3. 구동 방법·시뮬레이션

화면 흐름 계획: 쟁탈 도착 → 공연 진입 → 트럭·관객석 → 결과·정산 → 보드 복귀 · 현재 게릴라 공연 실행 모듈 없음 · 화면 캡처 미완 · 이식 비교 해당 없음.

이 기획의 실제 실행 버튼은 아직 없습니다. [쟁탈전 시뮬레이터](../../../../game-simulator.html?module=simulator_module_stage_battle)는 현재 출연권 대전을 살펴보는 도구이며 게릴라 공연이 구현됐다는 증거가 아닙니다. 서버 결과 생성·관객석 선택·팬 이동을 연결한 뒤 실제 한 판과 복귀를 검수합니다.

## 4. 상세 기획

### 한 판 순서

| 점검 | 기획한 처리 |
|---|---|
| 시작·종료 | 쟁탈 도착에서 공연으로 들어가고 결과 확인·보드 복귀로 마칩니다. 진입 갈림 자체는 작업전입니다. |
| 입력·출력 | 입력은 상대·보드 도착·주사위 배수, 출력은 팬 종류·등급·돈·팬·보상 기록을 계획합니다. |
| 상태와 전이 | 공연 준비 → 좌석 선택 → 세 명 완성 → 결과 공개 → 정산·복귀입니다. |
| 판정 | 결과와 공개 순서는 서버가 미리 정하고 좌석을 고르는 행동은 그 결과를 보여 주는 연출로 계획합니다. |
| 오류·예외 | 같은 좌석 재선택, 서버 실패·중단·재접속·상대 잔액 부족을 다룰 규칙은 작업전입니다. |
| 저장·복원 | 선택 기록과 판 결과를 복원하고 중복 지급을 막는 서버 기록이 필요합니다. 아직 구현되지 않았습니다. |
| 다른 모듈 연결 | 주사위·상대 선택·지갑·팬층·카드·몬스 기분과 상대 알림이 필요합니다. |

### 트럭과 관객석

1. 무대 트럭이 도착하고 짐칸 해치가 열리면 상대 팬들이 앞쪽 좌석에 모입니다.
2. 플레이어가 닫힌 좌석을 누를 때마다 조명이 해당 팬을 공개합니다. 한 번 연 자리는 다시 열지 않습니다.
3. 같은 종류가 두 명이면 일부 좌석에 반짝임을 보여 줍니다. 이는 다음 선택의 긴장감을 만드는 연출입니다.
4. 같은 종류 세 명이 먼저 모이면 해당 종류와 등급으로 판을 마치고, 모인 팬들이 우리 팀을 응원하며 무대로 올라옵니다.
5. 보상과 팬 이동 결과를 확인하고 트럭이 떠난 뒤 보드로 돌아갑니다.

좌석 수, 팬 종류의 이름·모양, 3명이 모이지 않는 경우와 연출 시간은 결정 대기입니다. 서버가 등급·종류·배치·공개 순서를 저장한다는 설계는 작업전이며, 좌석 선택의 위치와 공개 순서가 어떻게 결합되는지는 개발 전에 구체화해야 합니다.

```mermaid
flowchart TD
 A[서버가 판의 결과와 공개 순서 준비] --> B[닫힌 관객석 표시]
 B --> C[좌석 하나 선택]
 C --> D[팬 또는 숨은 응원봉 공개]
 D --> E{같은 팬 세 명}
 E --> F[해당 등급과 종류로 종료]
 E --> G[계속 선택]
 G --> C
```

### 결과 등급·보상 종류

| 구분 | 기획한 역할 | 남은 값 |
|---|---|---|
| 소·대·대박 | 먼저 세 명이 모인 결과의 등급 | 등급 이름·확률·보상 크기 발란스 대기 |
| 이벤트 전용 네 번째 등급 | 기간에만 추가할 수 있는 후보 | 기간·확률·이름 결정 대기; 무대 대결의 메가와 별개 |
| 돈 | 상대의 보유 돈을 기준으로 하는 공연 수익 | 지급량·상대 손실·단위 발란스 대기 |
| 카드 | 팬 종류에 따른 보상 후보 | 카드의 출처·수량·확률 작업전 |
| 기분 간식 | 몬스 기분에 연결할 보상 후보 | 공급량·기분 반영 작업전, 발란스 대기 |

등급과 보상 종류를 좌석에서 어떻게 함께 나타내고 서버가 어떤 조합으로 정할지는 결정 대기입니다. 과거에 논의된 금액·갈림 비율을 확정값으로 옮기지 않습니다.

### 숨은 응원봉과 돈 계산

일부 좌석에는 팬 대신 숨은 응원봉을 놓는 안입니다. 응원봉을 열면 주사위 배수와 함께 돈 보상에 적용하며 한 판의 합계 상한을 둡니다. 배수 크기·상한·출현 확률과 선택 횟수를 쓰는지는 발란스 대기입니다. 응원봉과 조명은 다른 요소입니다. 조명은 팬을 공개하는 연출이고 응원봉은 보상에 영향을 주는 별도 자리입니다.

공연을 연 사람의 보상과 상대가 잃는 돈은 각각 계산합니다. 상대가 가진 돈을 기준으로 삼는 방향은 있으나, 두 값의 차이와 보호선·하루 한도·새 돈 발생 여부는 정해야 합니다. 상대 잔액이 없을 때 임의 금액을 만들지 않고 그 경계의 처리 방식을 결정해야 합니다.

```mermaid
flowchart LR
 A[상대 보유 돈] --> C[공연 보상 기준]
 B[팬 등급과 보상 종류] --> C
 C --> D[주사위 배수]
 D --> E[응원봉 배수와 상한 검토]
 E --> F[내가 받는 결과]
 A --> G[상대가 잃는 양 별도 계산]
 F --> H[한 번에 정산하도록 설계]
 G --> H
```

### 팬 이동과 상대 알림

공연으로 데려오는 팬은 상대 팬이며, 기획은 내 팬 수 증가와 상대 계정의 팬 수 감소를 같은 이동으로 다룹니다. 관객석의 **세 명**은 결과를 보여 주는 상징이며 실제 이동 인원을 세 명으로 확정하지 않습니다. 실제 이동량은 등급·종류에 따라 발란스 대기입니다. 팬 수에 주사위 배수를 적용할지, 어떤 팬층에서 이동할지, 최소 보호선과 하루 한도는 결정 대기입니다.

상대가 다음에 접속하면 공연을 당한 내용을 확인하도록 계획합니다. 여러 판을 묶는 방법, 접속 중 상대 처리, 봇의 팬 보관과 기존 알림과의 통합은 작업전입니다. 돈과 팬을 각각 따로 중복 반영하지 않도록 저장·복구 경계를 설계해야 합니다.

```mermaid
flowchart LR
 A[결과에 따른 이동량 결정] --> B[내 팬 증가]
 A --> C[상대 팬 감소]
 B --> D[돈과 팬의 정산 기록]
 C --> D
 D --> E[상대 접속 시 알림]
 D --> F[같은 판 다시 열기]
 F --> G[새 지급 없이 결과 복원]
```

### 필요 시스템

쟁탈 진입 선택, 상대 선택, 서버의 판 생성과 공개 기록, 좌석 UI, 돈·팬 정산, 카드·간식 지급, 재접속 복원과 상대 알림이 필요합니다. 각각 별도 모듈·표를 참조하는 방향이며 아직 구현된 기능으로 간주하지 않습니다.

- 공연으로 진입한 같은 도착의 배수와 상대를 확인하고, 저장된 결과를 좌석 공개에 일관되게 사용합니다.
