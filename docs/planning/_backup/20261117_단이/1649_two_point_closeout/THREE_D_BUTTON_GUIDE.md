## 최신 .28 · 사용자 눈높이/소실점 참고를 실제2점투시에 적용
현중: “위쪽이 짧아져야지…원근인데…버튼이 너무 크게 눌려…살짝만”, “이런걸 참조하라는 거야”와 눈높이선/1·2·3점투시 참고2장.
일반 이론 설명에 그치지 않고 같은 카메라에서 실제 점들을 투영했습니다. 아래의 수치는 둥글리기 전 제작용 기준 사각형의 값이며 원본 카메라/원본 눌림 측정값이나 사용자 확정 숫자가 아닙니다.
현재r300/12화면940부품20연결. FullStateGraphic은 고정하고 Content그룹만2논리px 이동합니다. 기본/눌림 원화는 같은3D원형·시점·밑면에서 계산한 별도 전체입체 그림입니다. 실제mouse3초/Space3초의 상태교환/복원,390/430비율/이미지로딩을 확인했습니다. 원본GO서체/세부재질/원본동등·실게임·최종승인은 미완료입니다.
[실제 소실점/확대 도면·두 상태와 native결과](reference/two-point-button-20261117/index.html)를 보세요. 이전 생성3원화는 계속 실패보존본입니다. 이번source새패키지/3D런타임/제품코드변경0, 계산된벡터→PNG/WebP자원과native편집만 사용했습니다.

## .28 실제 2점투시 도면과 살짝 눌림

### 먼저 선택하는 것: 눈높이와 소실점
- 1점: 물체의 한 면이 화면에 평행한 배치에서 깊이 방향 선묶음이 한 소실점에 모입니다.
- 2점: 두 가로 방향 선묶음이 같은 눈높이선 위 좌우 소실점으로 모이고, 카메라를 기울이지 않은 이 모델에서는 수직 두께선이 수직입니다.
- 3점: 위/아래로 카메라를 기울여 수직 방향도 수렴하면 세 번째 소실점을 사용합니다.
- 물체가 눈높이 아래여서 윗면이 보인다는 사실만으로3점투시가 되는 것은 아닙니다.
- 이번 재현은 카메라 자체를 기울이지 않고 높은 눈높이 아래에 버튼을 둔2점투시입니다. 억지 마름모를 세로로 누르거나 비틀지 않습니다.
- 둥근 곡선 전체를 한 직선처럼 연장하지 않습니다. 원형의 기준 사각형·두 직교 방향·밑면 대응점에서 소실점을 먼저 확인하고 그 안에서 모서리 곡률을 만듭니다. 주신 원기둥 예시도 기준 박스/평면을 먼저 쓰는 이유가 같습니다.

### 직접 계산한 예
월드 X는 좌우, Y는 카메라에서 멀어지는 방향, Z는 높이입니다. 렌즈의 광축은 수평이며 소실점/눈높이는 상태에 따라 바뀌지 않습니다.

    u = cx + f * X / (D + Y)
    v = horizon + f * (eyeZ - Z) / (D + Y)

D+Y가 양수인 점만 유효합니다. 이 식은 원근 나눗셈을 포함하며 단순2D평행이동/직교투영과 다릅니다. 원형을 평면에서45도 배치한 두 방향의 소실점은 (cx-f,horizon), (cx+f,horizon)입니다.
구체 제작예는 D14,f1400px,cx115,horizon-1173px. f는 이 도면의 투영 스케일이며 실물 카메라의 초점거리mm가 아닙니다. 소실점(-1285,-1173)/(1515,-1173)은230×220 버튼 프레임 밖에 있습니다. 버튼 프레임에 맞춰 소실점을 가까이 당기면 과도한 광각 왜곡이 됩니다.

|기준점|기본 위치(px)|눌림 위치(px)|
|---|---|---|
|먼 위쪽|(115,10)|(115,11.7333)|
|왼쪽|(15,94.5)|(15,96.3571)|
|오른쪽|(215,94.5)|(215,96.3571)|
|가까운 아래쪽|(115,192)|(115,194)|

먼 위쪽 절반84.5px < 가까운 아래쪽97.5px, 먼 기준변130.9px < 가까운 기준변139.7px입니다. 위쪽이 반대로 길어지는지 눈대중으로만 판단하지 않고 두 모서리 선묶음이 각각 동일 소실점으로 수렴하는지 외적으로 검사했습니다. 밑면/윗면/눌린면 모두 같은 소실점입니다.
위표는 둥글리기 전 기준 사각형입니다. PNG의 칠해진 알파 경계나 원본 게임의 실제RectTransform을 뜻하지 않습니다.

### 큰 눌림 대신 작은 물리 높이 변화
밑면Z=0을 고정하고 윗면만 h→h-p로 변경했습니다. 이번 예는 p/h≈8.33%, 화면 기준 윗면 이동은 먼점1.733/중앙1.857/가까운점2px입니다. 밑면은 움직이지 않습니다.
도구의 거리0~16px는 지원 범위이지 기본 눌림값이 아닙니다. 이번 GO 콘텐츠는5→2px로 줄였습니다. 2px도 이번 제작 제안이며 모든 크기의 모든 버튼에 승인된 공통 상수로 복사하지 않습니다.
카메라를 그대로 둔 원근에서는 높이에 따라 화면상의 변 길이가 미세하게 달라질 수 있습니다. 물체 자체의 가로/세로 원형을 바꾸지 않는다는 것과 모든 투영 픽셀이 완전히 고정된다는 것은 다릅니다.

# 입체 버튼 제작법 — 기준면·원근·두께·상태 원화
작성 codex(단이) · 2026-11-17 16:07 KST · 가이드 .27 · 제작 규칙/수치 제안은 구분

## 이 규칙이 생긴 이유
현중: “찌그러졌어..이것도 만들때 기초 즉..원근법을 배워서 해야 돼..이거 가이드 넣어야 돼 입체 버튼의 만드는 법”.
r299의 평면 앞면+동작 효과와 이후 image_gen normal_v001/pressed_v001/pressed_v002 모두 원본 동등 시안으로 받아들여지지 않았습니다. 이 파일을 읽는 AI는 실패 그림/과거 수치/엔진 시험 통과를 정식 제작법으로 재사용하지 않습니다. 새 생성보다 아래 구조 연구가 먼저입니다.

## 1. 입체의 기초 — 한 물체, 한 시점
입체 버튼은 둥근 마름모를 아무렇게나 늘인 그림이 아닙니다. 같은 물체의 윗면·밑면·측면이 한 투영 규칙으로 이어져야 합니다.

- 원근 투영: 멀리 있는 부분은 작게 보이고 같은 방향의 평행선은 소실점 쪽으로 모입니다.
- 평행/직교 투영: 거리 때문에 크기가 변하지 않고 평행한 모서리는 화면에서도 평행합니다. 시점 각도에 따른 면의 단축은 여전히 있습니다. “직교니까 눌린 마름모로 그려도 됨”이라는 뜻이 아닙니다.
- 한 버튼에 윗면은 원근, 측면은 임의의 평행 복사, 하이라이트는 다른 시점의 둥근 형태를 섞지 않습니다.
- 정사각형을 화면에서45도 돌리는 것과, 기울어진 입체의 윗면을 카메라로 보는 것은 다른 연산입니다.
- 단일 스크린샷으로 원본 카메라/소실점/3D 모델을 확정하지 않습니다. 관찰값과 재현에 선택한 투영 모델을 따로 기록합니다.

공식 개념 근거: [Blender Cameras](https://docs.blender.org/manual/en/latest/render/cameras.html?highlight=lens+type). 이 프로젝트에 Blender 설치/3D 엔진 추가를 요구하는 규칙이 아닙니다. 벡터·2D 드로잉에도 같은 기하 원리를 적용합니다.

## 2. 색칠 전에 만들어야 하는 기초 도면
참고 이미지를 UI 전체 폭과 공통 하단선으로 정렬한 뒤 아래를 기록합니다. 각 부품을 독립적으로 가로/세로 늘려 겉보기만 맞추지 않습니다.

|기초값|기록할 내용|
|---|---|
|기준 캔버스|W/H, 피벗, 중앙축, 바닥 기준선, 단위/참고 이미지 크기|
|윗면 원형|원래 가로/세로 비율, 꼭짓점/중점, 모서리 곡률과 접선|
|투영|직교/원근 가정, 시점 기울기, 투영축 또는 소실점, 화면 배율|
|두께|같은 입체 높이 축, 윗면-밑면 대응점, 보이는 좌/우/아래 측면|
|베벨|모서리를 깎은 좁은 면의 폭/곡률/연결. 장식용 굵은 빛 테두리와 구분|
|광원/재질|광원 방향, 밝은 면/어두운 면, 광택의 범위와 세기|
|상태|기본 높이h, 눌림 깊이p, 밑면 고정, 텍스트/아이콘 기준점|

우선 단색 선과 면으로 도면을 만듭니다. 중앙축·곡률·두께가 일관된 뒤에만 그라데이션과 광택을 넣습니다. AI 생성에 맡겨도 이 도면/마스크를 기준으로 삼고 결과가 도면을 어겼으면 다시 생성한 사실을 완료로 세지 않습니다.

## 3. 측면을 만드는 원리
윗면과 밑면의 같은 꼭짓점/곡선 지점을 짝지어 연결합니다. 대응점마다 제각각 다른 방향으로 옮기면 옆면이 비틀리거나 한쪽만 부풀어 보입니다.

평행 투영으로 재현하기로 선택했다면, 모든 점에 같은 고정2×3 투영행렬 M과 배율/이동 c를 사용합니다. 밑면은 z=0, 기본 윗면은 z=h입니다.

    base_i    = M · (x_i, y_i, 0) + c
    normal_i  = M · (x_i, y_i, h) + c
    pressed_i = M · (x_i, y_i, h-p) + c

같은 높이차는 같은 화면 방향의 벡터가 됩니다. p를 바꾼다고 물체 자체의 x/y 가로·세로, 카메라, 중심, 모서리 원형이 바뀌지 않습니다.
원근 투영을 선택하면 원근 나눗셈까지 같은 카메라로 다시 투영해야 하며, 위의 일정한2D 이동식을 그대로 섞어 쓸 수 없습니다.

이 식은 재현용 제작 모델입니다. 원본 게임이 이 카메라나 h/p값을 쓴다는 뜻이 아닙니다. 실제 원본에서 관찰되지 않은 쿠션 변형/비선형 압축도 임의로 추가하지 않습니다.
[공식 Extrude Faces](https://docs.blender.org/manual/en/latest/modeling/meshes/editing/face/extrude_faces.html), [Extrude Along Normals](https://docs.blender.org/manual/en/latest/modeling/meshes/editing/face/extrude_faces_normal.html)의 구분을 참조합니다. 면의 두께와 정점별 팽창은 다릅니다.

## 4. 베벨·명암·외부 그림자는 서로 다른 역할
베벨은 모서리를 좁은 연결 면으로 깎아 빛이 걸리게 만든 형상입니다. 윗면과 측면 사이에 연속되는 폭과 곡률을 유지합니다. 원본에 없는 볼록한 베개 테두리나 트레이를 생성해 입체감을 대신하지 않습니다. [공식 Bevel 설명](https://docs.blender.org/manual/id/4.2/modeling/meshes/editing/edge/bevel.html)은 폭·구간·단면 형상을 구분합니다.

- 윗면 색/측면 명암/안쪽 접촉 음영/베벨 하이라이트는 원화의 재질 표현입니다.
- 버튼 밖 바닥에 드리우는 외부 투영 그림자는 엔진 효과로 분리합니다.
- 측면이 어둡다고 투명하게 지우거나 전부 엔진 drop-shadow로 대체하지 않습니다.
- 같은 광원이라면 기본/눌림에서 밝은 면의 방향이 뒤집히지 않습니다.
- “더 반짝임”으로 기하 오류를 숨기지 않습니다. 원본이 절제된 재질이면 강한 플라스틱 광택을 추가하지 않습니다.

## 5. 기본·눌림은 같은 마스터에서 만든 별도 입체 그림
|유지할 것|눌림에서 달라지는 것|
|---|---|
|같은 기준면/투영/시점/배율/피벗/밑면/광원|윗면 높이h→h-p|
|물체의 실제 가로/세로와 모서리 원형|보이는 측면 두께 감소와 접촉부 변화|
|공통 캔버스·부품 기준선|필요한 범위의 베벨·접촉 명암|
|같은 텍스트 역할/동작 연결|관찰·제작된 앞면 이동에 맞춘 콘텐츠 위치|

기본 그림부터 입체여야 합니다. 눌림은 별도 입체 상태 원화를 만들고 엔진의 이미지 전환 방식에 연결합니다. 기본 그림을 단순히 어둡게 하거나 전체를 아래로 이동시키는 것은 위의 눌림 원화를 대신하지 못합니다.
눌림 때문에 원본에 없던 테두리 트레이가 새로 생기거나, 전체 윗면이 임의로 길쭉해지는 결과는 반려합니다. 상태별 완전히 독립 생성보다 같은 마스터의 같은 기하에서 파생하는 방법을 우선합니다.

## 6. 텍스트·입력·배수·프레임 분리
- GO/수치/가격/안내는 native 텍스트, 화살표는 독립 부품, 버튼은 상태 이미지입니다. 화면 캡처나 글자까지 포함한 버튼 한 장을 붙여 완료하지 않습니다.
- 텍스트가 항상 면과 같은 원근으로 기울어진다고 추정하지 않습니다. 원본 GO 글자는 화면 기준으로 서 있는 그래픽에 가깝습니다. 실제 보이는 정렬을 따르며 폰트/전용 글리프와 몸체 투영을 구분합니다.
- 입력 wrapper는 고정. 전체 입체 상태 이미지와 별도 콘텐츠 그룹은 구분합니다. 배수/알림/외부 받침은 별도 계층입니다.
- 상태 원화에 윗면 이동이 이미 그려져 있으면 같은 이미지에 pressFeedback translate를 중복 적용하지 않습니다. 텍스트 그룹만 실제 앞면 이동에 맞춰 동기화할 수 있습니다.
- 자식에서 버튼으로 입력이 전달되려면 중간 그룹의 parent 경로도 확인합니다. 키보드와 마우스를 각각 검수합니다.
- 현재 도구에는 tint/image5상태와 선택적 pressFeedback0~16논리px가 있습니다. 새 그림의 콘텐츠 이동량이 이 범위를 넘으면 그림을 눈속임으로 왜곡하지 말고 필요한 툴 보완을 별도 명세/시험합니다. 아직 구현하지 않은 동작을 지원 완료로 쓰지 않습니다.

## 7. 가변형 박스·9슬라이스·반응형
사각 바탕/프레임의 공통9슬라이스 원칙은 유지합니다. 그러나 독특한 마름모 입체 버튼을 좌우로만 늘려 원근·모서리를 찌그러뜨리면 안 됩니다.
- 중앙 입체 버튼은 기본적으로 동일 비율로 확대/축소하고 좌우 바는 별도 가변 영역으로 둡니다.
- 가변 사각 입체 버튼이 필요하면 앞면/측면/베벨의 분할 경계를 맞추고 고정 모서리·두께·높이를 함께 검수합니다.
- 부모 입력 크기/자식 그림의 알파 경계/텍스트 영역/레이아웃 셀 규격을 따로 측정합니다. 같은 메뉴 규격이 모든 원화의 실루엣을 같은 네모로 강제한다는 뜻은 아닙니다.

## 8. 자원 출력과 기본/눌림 정합
파일 예: UI_Main_Roll_Button_Normal_vNNN.png / UI_Main_Roll_Button_Pressed_vNNN.png. 프로젝트의 기존 네이밍 규칙을 우선합니다. native Txt_Roll_GO 등 역할 이름/flat key와 그림 파일 이름은 별도입니다.

원본/master·프롬프트·수정본·SHA를 보존하고 production은 별도 버전으로 만듭니다. 기본/눌림은 같은 W/H, 피벗, 가로 중심, 바닥 기준점을 공유합니다. 버튼 바깥은 alpha0이고 의도하지 않은 사각 배경·외부 그림자를 포함하지 않습니다.
상태별로 alpha bounding box를 각각 잘라 재중앙정렬하면 윗면이 내려간 효과를 없애거나 전체가 튑니다. 기본 그림의 타이트한 외곽을 기준으로 공통 상태 캔버스를 정하고, 눌림의 윗면 위 여백은 그 공통 좌표 안에서 보존합니다.
단순 패딩/위치 맞춤으로 서로 다른 투영의 그림이 올바른 입체가 되는 것은 아닙니다. 기하를 먼저 다시 만들어야 합니다.

## 9. 통과 판단 순서
1. 단색 도면에서 기준면의 가로/세로, 네 방향 곡선, 중심축, 대응점과 두께 방향을 대조합니다.
2. 기본/눌림을 같은 폭·밑면·시점으로 겹쳐 물체 크기가 불필요하게 변하지 않는지 확인합니다.
3. 원본 비교는 UI 전체 폭/하단선으로 정렬하고, 글자·측면·베벨·외부 그림자를 각각 확인합니다.
4. 원화만 전환해 보는 검수와 도구의 실제 mouse/keyboard/해제/취소 검수를 구분합니다.
5. 390/430 등 기기와 가변 논리 폭에서 원근/비율·공통 메뉴 기준선/입력 영역을 재확인합니다.
6. 저장·재열기·원본/다른 화면 보존을 확인하고, 현중이 특정판을 컨펌한 경우에만 승인판/수치로 승격합니다.

허용 오차와 눌림 깊이/색/재질은 승인 전 제안입니다. 자동시험 수·파일 생성 성공·이미지 생성 성공을 시각 합격이나 완성률로 쓰지 않습니다.
