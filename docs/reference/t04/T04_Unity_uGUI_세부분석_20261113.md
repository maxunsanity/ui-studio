# Unity uGUI 세부 분석 · UI 스튜디오 구현 기준

작성 codex(단이) · 2026-11-13 17:06 KST · 제안(검수 대기)

## 분석 결론

우리 툴은 현재 **부품·입력 역할·이미지 조립의 기초는 있지만 uGUI와 같은 기능을 가진 단계는 아닙니다.** 모노폴리 GO의 전 화면을 재현하려면 좌표·그리기 순서·입력·컨트롤 상태·자동 배치·스크롤을 공통 기능으로 보완해야 합니다. 도형과 이름이 있는 것만으로 해당 컨트롤이 구현됐다고 세면 안 됩니다.

먼저 모노폴리 GO를 기준으로 샘플과 기능을 검증하고, 우리 게임에 맞추는 작업은 그 이후에 합니다. 현재 로비의 메뉴 배치 변경은 툴의 직접 편집 시험이며 모노폴리 GO 재현 완료를 뜻하지 않습니다.

## 1. 조사 기준과 범위

Unity 공식 uGUI 저장소의 문서와 공개 C# 소스를 읽었습니다. 조사 당시 main의 package.json은 **com.unity.ugui 7.0.0**입니다. 이는 공개 소스의 기준 버전이며 모노폴리 GO에 사용된 Unity/uGUI 버전이나 정식 최신 배포판을 확인했다는 뜻은 아닙니다. main 문서에 새로 있는 기능을 모든 구버전에 존재한다고 적용하지 않습니다. [공식 패키지 정의](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/package.json)

이 분석은 런타임 GameObject 기반 uGUI를 대상으로 합니다. Unity 에디터 자체를 만드는 UI Toolkit·IMGUI와 구별합니다. 우리 툴에서의 기능 대응은 웹 기반 구현 계획이며 Unity 실행 파일·Prefab·Shader까지 호환된다고 보증하지 않습니다.

## 2. 기본 구조: 사각형은 그림도 버튼도 아닙니다

하나의 UI 요소는 역할이 다른 컴포넌트를 함께 가질 수 있습니다. RectTransform은 배치, Image는 그림, Button은 클릭과 상태를 담당합니다. 따라서 ‘박스 안에 이미지를 넣으면 박스가 보이지 않아야 한다’는 요구는 배치 사각형과 렌더링을 분리해야 해결됩니다. 편집 선택 테두리도 게임 그림으로 저장하지 않습니다. [기본 배치](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/UIBasicLayout.md), [시각 컴포넌트](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/UIVisualComponents.md)

상단 HUD 샘플의 제안 계층은 다음과 같습니다. 하나의 Image를 반드시 바탕과 프레임 두 개로 나누는 것은 아닙니다. 같은 원본 Sprite가 둘을 함께 담당할 수도 있으므로 실제 자원과 편집 목적에 맞춰 조립합니다.

- 화면 Canvas / 기준 해상도·화면 배율
- 안전영역 루트 / 노치·제스처 영역을 피하는 배치
- 상단 정보 바 / RectTransform과 배경·프레임 이미지
- 재화 표시 그룹 / 아이콘 이미지와 별도 숫자 텍스트
- 메뉴 버튼 / 입력 영역과 상태, 그 안의 그림·아이콘·배지
- 펼침 메뉴 / 백판과 항목 목록, 열림 상태, 입력 차단·복귀 정책

재화 숫자는 표시 전용일 수 있고, 같은 재화 영역에 상세 열기 기능이 있다면 그 영역에만 입력을 추가합니다. 바탕 그림의 존재로 클릭 가능 여부를 추정하지 않습니다. uGUI에서도 시각 컴포넌트와 상호작용 컴포넌트는 별개입니다. [상호작용 컴포넌트](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/UIInteractionComponents.md)

## 4. 좌표·화면 크기에서 반드시 맞춰야 할 것

RectTransform의 앵커는 부모에 대한 비율이고, 고정 위치·폭·높이나 늘림 여백을 함께 사용합니다. 피벗은 회전·배율·크기 변경의 기준점입니다. Unity의 UI 좌표와 브라우저의 위쪽 기준 Y를 그대로 섞지 않도록 변환 규칙을 문서화해야 합니다. ‘부모 폭의 50% 위치’ 하나만으로는 우측 고정 버튼과 양쪽 늘림 백판을 같은 방식으로 재현할 수 없습니다. [RectTransform 배치](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/UIBasicLayout.md)

Canvas Scaler는 기준 해상도와 화면의 차이를 처리합니다. 반면 지금 툴의 50%·100% 확대는 편집을 위한 보기 배율입니다. 둘을 별도 저장해야 합니다. Match Width/Height의 중간값은 단순 산술 평균이 아니라 소스에서 로그 공간의 보간으로 계산합니다. 공식 코드에 대응하는 식은 `s = (W/Wref)^(1-m) × (H/Href)^m`입니다. Expand는 두 비율 중 작은 값, Shrink는 큰 값을 사용합니다. [CanvasScaler 소스](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Runtime/UGUI/UI/Core/Layout/CanvasScaler.cs#L296)

Safe Area는 노치와 시스템 영역을 피해 자식을 배치하는 기준입니다. 현재 main 문서는 안전영역을 읽어 RectTransform 앵커에 적용하는 컴포넌트를 설명합니다. 이 새 컴포넌트 존재를 모노폴리 GO의 사용 버전에 그대로 단정하지 않습니다. 우리 툴에서는 기기별 가상 안전 여백을 시험하고, 장식 배경은 전체 화면을 채우되 조작부는 안전영역에 맞추는 구조가 필요합니다. [공식 Safe Area 문서](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-SafeArea.md)

제안 데이터 항목: anchorMin/anchorMax/pivot/anchoredPosition/sizeDelta 또는 offset, referenceResolution/scaleMode/matchMode/match, safeArea 기준. 이 목록은 구현된 JSON 필드가 아니라 새 좌표 계약의 검토안입니다. 기존 schemaVersion3를 조용히 다른 의미로 해석하지 않고 변환·원복·구버전 검증을 마련해야 합니다.

## 5. 이미지: 자원과 부품과 상태를 분리합니다

Image Type은 Simple·Sliced·Tiled·Filled로 구별됩니다. ‘3슬라이스’는 별도 uGUI Image Type이라기보다, Sliced의 상하 border를 0으로 둔 좌·중·우 구성을 대응시키는 방식으로 정리할 수 있습니다. 이는 우리 툴의 표현 대응안이며 픽셀까지 일치한다고 시험한 것은 아닙니다. [Image 유형](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/UIVisualComponents.md)

개별 자원은 원본 크기·Sprite 경계·기준 픽셀 밀도·출처를 갖고, 요소는 그 자원과 표시 방식·색·크기·상태를 참조하도록 합니다. 같은 작은 백판 이미지를 여러 버튼에 재사용할 수 있어야 합니다. 분할선과 화면 테두리 폭을 같은 숫자라고 강제하면 해상도나 기준 배율이 달라질 때 어긋날 수 있습니다. [Image 속성](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-Image.md), [Canvas Scaler](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-CanvasScaler.md)

진행 바·쿨다운에는 Filled의 채움 방향·시작점·채움량이 필요합니다. 원형 그림을 가로로 잘라 보이는 것과 방사형 채움은 다른 기능입니다. 원형 프로필의 자르기도 원형 프레임을 위에 올리는 것만으로는 해결되지 않습니다.

## 6. 입력과 상태: 보이는 것과 눌리는 것은 다릅니다

GraphicRaycaster 소스는 입력 대상 여부, 사각 범위·입력 여백, 추가 필터를 확인하고 깊이 순으로 후보를 정렬합니다. 우리 툴도 편집 선택의 맨 위 부품과 게임 입력의 대상이 다를 수 있어야 합니다. 장식 이미지가 클릭을 가로채지 않게 하고, 겹침·잘림·부모 그룹의 차단 정책을 입력 판정에 반영해야 합니다. 현재의 ‘부모에 전달’은 도구의 정책이며 Unity의 모든 이벤트 전파 규칙과 같다고 볼 수 없습니다. [GraphicRaycaster 소스](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Runtime/UGUI/UI/Core/GraphicRaycaster.cs#L276)

Selectable의 현재 소스 상태는 Normal·Highlighted·Pressed·Selected·Disabled입니다. 일부 문서는 Selected를 빠뜨린 4개 상태로 설명하므로 소스와 대조했습니다. 우리 툴의 기본·눌림·선택·비활성 네 상태는 Highlighted와 다릅니다. 편집에서 선택한 레이어와 게임에서 선택된 버튼도 별도 상태로 취급해야 합니다. [Selectable 상태 소스](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Runtime/UGUI/UI/Core/Selectable.cs#L701)

색 변화·Sprite 교체·애니메이션 중 무엇이 바뀌는지, Target Graphic이 어떤 자식인지 지정해야 합니다. 누르기만 했을 때와 눌렀다 놓아 클릭이 완료됐을 때도 구별합니다. [상태 전환](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-SelectableTransition.md), [Button](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-Button.md)

게임 실행 이벤트에는 enter/exit/down/up/click, drag 시작/이동/종료, drop, scroll, select/deselect, submit/cancel이 있습니다. 편집용 드래그 손잡이가 작동한다고 게임의 카드 드래그 기능이 생긴 것은 아닙니다. 방향키 포커스 경로 역시 편집 단축키와 구별해 설계합니다. [지원 이벤트](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/SupportedEvents.md), [Navigation](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-SelectableNavigation.md)

## 7. 모달·시트·상세 페이지의 조립

공식 컴포넌트 목록에는 독립적인 범용 ‘모달’ 항목이 보이지 않습니다. 따라서 우리 도구의 모달은 CanvasGroup·Image·Button과 화면 상태·입력·복귀 정책을 조합한 상위 패턴으로 다루는 것이 적합하다는 판단입니다. 상세 페이지와 탑창·바텀창도 같은 방식으로 구성합니다. [공식 목차](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/TableOfContents.md)

CanvasGroup의 alpha·interactable·blocksRaycasts는 다른 속성입니다. 투명하게 보이게 한 것만으로 클릭이 꺼지지 않고, 비활성으로 만든 것과 뒤로 통과시키는 것도 다릅니다. 부모 그룹의 영향과 무시 여부도 고려합니다. [CanvasGroup](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/class-CanvasGroup.md)

공통 모달 정의에 필요한 항목은 백판/딤, 뒤 입력 차단, 바깥 클릭 닫기, 뒤로·취소 허용, 열릴 때 포커스, 닫은 뒤 복귀, 중첩 순서, 표시 연출과 연출 중 입력입니다. 바텀시트라는 위치가 자동으로 모달 여부를 결정하지 않습니다. 현재 consumer는 오버레이마다 backdrop을 만들고 모델은 토스트·팝오버의 차단을 예외 처리하므로 실제 DOM 차단과 상태 판정이 일치하는지 보완 검수가 필요합니다.

세부 페이지는 목록에서 선택한 항목 ID를 받아 표시하고, 돌아갈 때 필터·스크롤·선택·포커스를 복원해야 합니다. 특정 상품이나 카드의 데이터 값을 UI에 고정하는 대신 참조·시험 데이터를 분리합니다.

## 8. 목록·자동 배치·마스크

ScrollRect는 Viewport와 그 아래 단일 Content, 선택적 Scrollbar 구조를 갖습니다. 방향, 경계 모드, 관성·감속, 스크롤 이벤트가 별도로 있습니다. 우리 툴은 목록 모양을 제공하는 것에서 끝나지 않고 목록 콘텐츠가 커져도 이 구조로 동작해야 합니다. 스크롤 중 항목을 클릭할지, 드래그로 판정할지도 실제 시험해야 합니다. [ScrollRect](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-ScrollRect.md)

Mask와 RectMask2D는 자식 표시를 제한합니다. 전자는 스텐실을 이용하는 형태 마스크이고, 후자는 2D 사각 영역 제한입니다. 웹에서는 동일 GPU 구현을 복사하기보다 사각 클리핑·형태 마스크를 구분하고 입력 범위까지 일치시키는 기능 대응을 시험합니다. [Mask](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-Mask.md), [RectMask2D](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/script-RectMask2D.md)

자동 배치는 최소·선호·가변 크기와 그룹의 할당을 구분합니다. 내용 크기 맞춤과 부모의 자식 배치도 다른 역할입니다. 현재 ‘같은 간격 정렬’은 한 번 실행하는 정렬이며, 글자가 길어지거나 부모 폭이 바뀔 때 자동으로 다시 계산하는 LayoutGroup이 아닙니다. 자동 배치가 제어하는 값은 수동 입력과 충돌하지 않도록 읽기 전용 표시·해제 경로가 필요합니다. [자동 배치](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Documentation~/UIAutoLayout.md)

## 9. 가벼운 구현과 AI 사용 계약

uGUI 소스는 레이아웃 재계산과 그림 재생성 큐를 분리합니다. 우리 웹 도구에도 필요한 범위만 갱신하고 같은 프레임에 변경을 모으는 방식이 참고됩니다. Unity의 batching·draw call 수치를 웹 DOM 성능 수치로 옮기지는 않습니다. 목록·스토리보드는 보이는 부분 위주로 표시하고 유휴 상태의 상시 렌더 루프를 피합니다. [CanvasUpdateRegistry](https://github.com/Unity-Technologies/uGUI/blob/main/com.unity.ugui/Runtime/UGUI/UI/Core/CanvasUpdateRegistry.cs)

AI가 읽을 설계는 화면·부품 ID, 부모/형제 순서, 좌표 기준, 이미지 자원과 분할, 입력 대상, 값과 상태, 연결/전달/복귀, 출처와 검증 상태를 갖춰야 합니다. 실행 중 계산된 화면 좌표와 애니메이션 transform은 원래 배치 정본을 덮어쓰지 않습니다. 구조 보기와 게임 보기는 같은 설계와 실행 상태를 사용합니다.

## 10. 보완 순서와 시험 기준

| 순서 | 보완 대상 | 통과 기준 |
|---|---|---|
| 0 | 발견된 메뉴 뒤비침·속성 수정 반영 | 메뉴를 열어도 뒤 글자가 새어 나오지 않고 이름·표시글이 저장/재열기 후 유지 |
| 1 | RectTransform·Canvas 배율·안전영역·형제 순서 | 상단 바/우측 메뉴/아이콘/숫자가 폰·폴드·태블릿에서 규칙대로 유지 |
| 2 | Image 유형·독립 텍스트·5가지 버튼 상태·입력 여백 | 실제 그림을 넣어도 임시 박스가 없고 분할/상태/입력 도형이 일치 |
| 3 | CanvasGroup·클리핑·ScrollRect·자동 배치 | 모달/목록/상세의 입력 차단·스크롤·복귀·긴 내용이 정확 |
| 4 | Toggle/탭/Slider/Dropdown/InputField | 모양이 아니라 실제 값 변화·이벤트·취소·저장 상태까지 동작 |
| 5 | 전체 화면 확장·연출·성능·호환 출력 | Figma 화면 대조표의 분석/구성/시험/미확인 수를 관리하며 범위별 완료 판정 |

첫 상단 HUD 샘플의 제안 시험은 다음과 같습니다. 아래는 **수락 시험 계획이며 이번에 실행한 시험 결과가 아닙니다.**

- 기준 부모 너비를 바꿔도 지정된 상단·우측 여백과 고정 아이콘 크기를 유지합니다. Canvas 배율이 바뀌는 경우와 RectTransform 크기만 바꾸는 경우를 나눕니다.
- 피벗·앵커를 바꿀 때 현재 그림 위치 유지/원시 값 편집의 차이를 설명합니다.
- 버튼을 눌렀다가 밖으로 나가 놓으면 오동작하지 않습니다. 비활성·표시 전용·차단·부모 입력을 각각 시험합니다.
- 메뉴를 열면 7개 항목이 지정 순서와 간격으로 보이고, 접으면 보이지 않는 항목은 입력되지 않습니다.
- 딤의 유무·진하기와 뒤 입력 차단을 독립적으로 바꿔 시험합니다. 모달을 닫으면 원래 선택·스크롤·포커스가 돌아옵니다.
- 구조/게임 보기는 동일 ID·배치·입력·값·연결을 유지합니다. 이미지 교체만으로 기능이 달라지지 않습니다.
- 수정→undo/redo→저장→재열기 후 같은 결과가 나옵니다. 구버전 문서와 저장 충돌도 보존합니다.
- CSS1440/430의 편집기, 논리390×844/690×844/768×1024 화면을 구별합니다. 실제 기기와 메모리/FPS는 별도 측정합니다.

## 11. 이번 분석의 한계와 기록

이번에는 공식 문서·소스와 우리 툴 소스를 대조했습니다. Unity 에디터를 설치하거나 장면을 실행하지 않았고, 새로운 UI 기능 구현·런타임 시험·스크린샷 검수는 하지 않았습니다. 이전 88개 시험이나 r15의 메뉴 편집 결과는 과거 기록입니다. 이번 통과 수로 합산하지 않습니다.

main 문서와 소스가 서로 어긋나는 항목(Selectable 상태)은 소스 근거를 함께 남겼습니다. TMP 세부 셰이더/폰트 렌더링, 멀티터치·Input System 전체, 월드 공간 Canvas, Unity Prefab 변환, 모노폴리 GO 내부 Unity 계층·전체 버전별 화면은 아직 상세 검증하지 않았습니다. Figma의 캡처는 실제 내부 설정을 증명하지 않습니다.

공개 소스 main은 움직이는 대상이므로 구현 시에는 사용할 Unity/uGUI 버전과 커밋 기준을 고정해야 합니다. 현재 보고는 열람 시점의 조사 결과입니다. 사용자 요청의 30% 계정 주간 한도 조건은 그대로 유지하며 조사 시작과 중간 조회는 8%였습니다.
